# المرحلة الثانية — تشغيل شركة ثنارة داخليًا

## نطاق التنفيذ

هذه مساحة الشركة الداخلية على `/company/`، وليست إدارة عيادات العملاء.
تستخدم المصادقة الحالية وMongoDB المركزي؛ لا تنشئ قاعدة SQL أو نظام اشتراكات
أو فوترة موازيًا. طلب المستخدم بدء المرحلة واعتمد سياسات قابلة للتهيئة
والاعتماد بدل افتراض نسب أو مبالغ مالية.

| المحور | السلوك المتاح |
| --- | --- |
| الهيكل | شركة، إدارات، أقسام، علاقات هرمية وفحص المراجع والأرشفة |
| الموظفون والوصول | ملفات موظفين، ربط حسابات منصة موجودة، أدوار جاهزة ومخصصة بقوائم صلاحيات صريحة |
| الموارد البشرية | عقود مؤرخة، أجر شهري، منع تداخل العقود المعتمدة، استحقاق رواتب بعقد يغطي الشهر |
| CRM | مراحل العميل المحتمل حتى الفوز/الفقد، التواصل، مدير الحساب |
| الطلبات | مسودة، إرسال، اعتماد/رفض مستقل، تصعيد إلى مسؤول مختلف مع سبب، متابعة التأخر |
| المحاسبة | دليل حسابات، قيود متعددة الأطراف، تسجيل سحب/إيداع بين حسابات أصول، ترحيل مستقل وقيد عكسي |
| الاستحقاقات | سياسات رواتب/عمولات/أرباح بمعدل وحد أعلى وحسابات وفترة سريان، اعتماد مستقل ولقطة احتساب |
| الإدارة | لوحات CEO وCTO والمدير التنفيذي العام، بأرقام فعلية بحسب صلاحيات كل دور |

## شرط الإغلاق — الضوابط المنفذة

- جميع المسارات الداخلية تتطلب هوية منصة وجلسة نشطة. غير المدير الجذري
  يحتاج ملف موظف نشطًا مرتبطًا بالحساب؛ عضوية عيادة لا تمنح صلاحيات الشركة.
- تُفرض الصلاحيات من الخادم؛ اختيار رابط أو تعديل الواجهة لا يمنح صلاحية.
  تغيير ربط الحساب والأدوار يتطلب صلاحية إدارة الوصول، ولا يجوز تعديل
  صلاحيات الملف الشخصي ذاتيًا. طلبات الموظف محدودة بنطاقه؛ CTO يرى النطاق
  التقني دون الرواتب أو المالية.
- اعتماد السياسات والعقود والطلبات وترحيل القيود يتطلب مراجعًا غير المنشئ.
  المستفيد لا يعتمد عقده أو يرحل استحقاقه الشخصي.
- تُحفظ العملية ونتيجتها وحدث التدقيق في معاملة واحدة. فشل حفظ التدقيق
  يلغي تعديل السجل. تحتوي إجراءات المراجعة سببًا ومرجع السجل وإصداره وهوية
  المنفذ، دون نسخ بيانات الرواتب داخل سجل التدقيق.
- المبالغ أعداد صحيحة بالهللات وSAR فقط؛ لا حساب مالي بالكسور العائمة.
  احتساب المعدلات يستخدم التقريب نصفًا لأعلى، ويظل الحد الأعلى قرارًا
  صريحًا في السياسة. كل قيد مرحّل موجب ومتوازن، ولا يدخل التقرير قيد مسودة.
- التقارير تُحسب من دفتر الفترة كاملًا، لا من صفحة القائمة المعروضة.
  يعرض ميزان المراجعة طرفي كل حساب والإجماليات والفرق والإيرادات والمصروفات.
- القيود المرحلة لا تُعدل ولا تُحذف؛ التصحيح بعكس مستقل يحتاج ترحيلًا.
  المسودات قابلة للإلغاء مع بقاء تاريخها، ويمكن إعادة احتساب مسودة ملغاة.
- يمنع مرجع العملية تكرار إعادة المحاولة، وتمنع مراجع الاستحقاق تكرار
  الراتب الشهري أو إعادة استخدام قيد إيراد للعمولة. تعاد مراجعة السياسة
  والعقد والأساس وقت الترحيل؛ لا تُرحّل نتيجة احتساب أصبحت قديمة.
- العمولة تتطلب عميلًا مكتسبًا ومدير حساب مطابقًا للمستفيد وقيد إيراد
  مرحّلًا مرتبطًا بالعميل والفترة. توزيع الأرباح يُحسب من صافي الدفتر،
  ولا يجوز أن يتجاوز مجموع التوزيعات ربح الفترة المتاح.

## دليل التحقق

- فحص TypeScript وبناء Nest: ناجحان.
- الاختبارات العامة: 1050 ناجحة، 100 متخطاة وقت التشغيل العام
  (تشمل اختبارات تكامل تحتاج تشغيلًا منفصلًا؛ لا تُحسب ناجحة في هذا الأمر).
- اختبارات المرحلة المنفصلة: 23 ناجحة على MongoDB replica set مؤقت،
  منها 4 اختبارات حسابية و19 اختبار تكامل. تشمل الصلاحيات، فصل المراجع،
  الاستفادة الذاتية، الفساد في بيانات المنشئ، الإلغاء عند فشل التدقيق،
  التزامن والتكرار، اعتماد السياسات، الحسابات والاستحقاقات والعكس
  والمطابقة عبر أكثر من صفحة.
- فحص الملفات الجديدة بـESLint: لا أخطاء؛ تحذيرات أنواع إرجاع صريحة غير مانعة.
- اختبار المتصفح المالي: نجحت رحلة المنشئ ثم المراجع المستقل والترحيل
  وميزان المراجعة والتدقيق على قاعدة مؤقتة معزولة. احتفظ النموذج ببنوده
  عند إضافة بند ثالث، وطابقت 70.01 + 30.04 قيمة 100.05 ريال في الطرفين،
  ولم يظهر الترحيل للمنشئ أو تعديل القيد بعد ترحيله.
- نجح دخول CTO المقيّد دون ظهور المالية والعقود والعمولات، ونجح فحص
  لوحته بعرض 390 بكسل دون تجاوز عرض الصفحة. لم يُفحص كل نموذج على الهاتف
  أو كل متصفح؛ توجد جداول قابلة للتمرير الأفقي عند الحاجة.
- أُعيدت المعاينة إلى اتصال التطوير المعتمد بعد الاختبار، وأُزيلت
  بيئة الاختبار المؤقتة. أعادت `/health` و`/ready` و`/company/` حالة 200،
  ونجح دخول المدير وقراءة جلسة الشركة وصلاحياتها ثم الخروج.
- كشف الاختبار الأول تعارضًا بين حقل قفل مستحدث ومخطط هوية صارم؛
  صُحح باستخدام بروتوكول إصدار المراجع القائم، مع تحقق المخطط المالك
  في اختبارات التكامل قبل إعادة الرحلة بنجاح.

## الإعداد والحدود

لبيئة التطوير المعتمدة فقط، بعد البناء:

```sh
node scripts/initialize-company-dev.cjs
```

ينشئ هذا الأمر فهارس ومجموعات الشركة فقط؛ لا ينشئ هيكلًا أو موظفين أو
رواتب أو حسابات مالية أو سياسات معتمدة. ملفات الشركة لا تخزن كلمات مرور؛
إنشاء هويات المنصة يتم عبر إدارة المنصة الحالية.

للاختبار المنفصل دون استخدام أي اتصال محفوظ:

```sh
DOCKER_HOST=unix:///var/run/docker.sock bash scripts/test-company-operations.sh
```

خيار `--browser-fixture` يشغل تطبيقًا اصطناعيًا معزولًا مؤقتًا لاختبار
المتصفح، وليس أمر تشغيل أو إعدادًا لبيانات الشركة الفعلية.

حدود يجب عدم إخفائها:

- هذه نسخة تطوير؛ ليست موافقة تشغيل إنتاجي أو إغلاق قبول المرحلة تلقائيًا.
- يلزم إدخال هيكل الشركة وملفات الموظفين ودليل الحسابات والسياسات الفعلية
  واعتمادها من أشخاص مخولين؛ لا توجد نسب أو أجور أو بيانات عمل تجريبية
  مزروعة في قاعدة التطوير المعتمدة.
- الرواتب هنا استحقاق شهري كامل. لا يُفترض احتساب أيام جزئية أو تأمينات
  أو ضرائب أو استقطاعات أو التزام نظامي محلي دون نطاق وسياسات معتمدة.
- استحقاق الراتب/العمولة/الربح ليس صرفًا أو حالة «مدفوع». السحب والإيداع
  تسجيل محاسبي فقط؛ لا اتصال بنك ولا تحويل أموال أو تفعيل Geidea.
- سجل التدقيق غير قابل للتعديل من واجهات النظام، لكنه ليس ادعاء حماية
  من مسؤول قاعدة بيانات يملك وصولًا مباشرًا إليها.
- قبل بدء هذه المرحلة لم تكن قبولًا رجعيًا للمرحلة الأولى. في 2026-11-15
  اعتمد المالك Phase 01 صراحةً بعد مراجعة نتائجها، وطلب بدء #111. يسمح ذلك
  بالعمل في التطوير فقط؛ لا يجيز ترحيل بيانات إنتاج أو النشر.

عقد API وحقول الواجهات في `docs/INTERNAL_OPERATIONS_API.md`.
