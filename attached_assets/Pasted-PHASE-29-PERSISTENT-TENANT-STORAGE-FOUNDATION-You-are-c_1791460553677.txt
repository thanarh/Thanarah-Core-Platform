==================================================
PHASE OBJECTIVE
==================================================

Build the persistent Tenant Storage Foundation required by the Phase 28 Patient storage boundary.

The end state must be:

Patient
  ↓
Tenant-scoped repository
  ↓
Logical Tenant Storage
  ↓
Persistent MongoDB storage
  ↓
Tenant-isolated physical database

The infrastructure must be designed so that one logical Tenant can eventually use multiple physical databases.

This phase establishes the storage infrastructure.

It does NOT implement database sharding, automatic provisioning, migration, rebalancing, or capacity management.

==================================================
1. INSPECT EXISTING ARCHITECTURE FIRST
==================================================

Before coding, inspect the current implementation for:

- TrustedTenantContext
- Tenant Storage Resolver
- Tenant Storage Registry
- Patient repository
- Phase 28 volatile storage adapter
- existing MongoDB dependencies
- Mongoose dependencies
- Prisma configuration
- environment/configuration modules
- application lifecycle hooks
- health/readiness checks
- test infrastructure
- tenant isolation tests

Do not create duplicate infrastructure if an existing abstraction already exists.

Extend the current Phase 28 architecture rather than replacing it with a parallel system.

==================================================
2. STORAGE ARCHITECTURE
==================================================

The architecture must distinguish:

LOGICAL TENANT STORAGE

from

PHYSICAL DATABASE STORAGE.

Conceptually:

Tenant
  ↓
TenantStorageRegistry
  ↓
LogicalStorageContext
  ↓
PhysicalStorageTarget(s)
  ↓
MongoDB database

The Patient domain must only know the logical tenant storage context.

It must never know:

- Mongo URI
- database name
- Mongo credentials
- physical database ID
- connection pool
- Mongo client

Those belong exclusively to infrastructure.

==================================================
3. TENANT STORAGE REGISTRY
==================================================

If an existing Tenant DB Registry contract exists, extend it.

If no registry exists, create the minimum production-oriented registry contract required for this phase.

The registry must conceptually support:

Tenant
  ↓
one or more physical storage targets

A registry entry should be capable of representing:

- tenant ownership
- storage target identity
- storage provider/type
- connection reference or secret reference
- database identifier/reference
- lifecycle/status
- primary/active target designation
- createdAt
- updatedAt

IMPORTANT:

Do NOT store raw MongoDB passwords or connection strings in normal domain records.

Do not expose secrets through APIs.

Use secret references/configuration indirection according to existing project conventions.

==================================================
4. CENTRAL MYSQL ROLE
==================================================

The central Prisma/MySQL database may store the STORAGE REGISTRY METADATA.

It must NOT store the Patient records themselves.

This is acceptable:

Central MySQL:
TenantStorageRegistry metadata

Tenant MongoDB:
Patient documents

This is NOT acceptable:

Central MySQL:
TenantStorageRegistry + Patient operational records

The central DB is control-plane metadata.

Tenant storage is data-plane healthcare storage.

==================================================
5. PHYSICAL STORAGE TARGET
==================================================

Do not hard-code:

tenantId → one Mongo database

The abstraction must support:

tenantId
  → logical storage
      → physical target A
      → physical target B
      → future target C

For this phase:

- one active physical target is sufficient for actual runtime
- multiple target representation must remain possible
- no sharding logic is required
- no automatic routing across multiple targets is required

Do not implement fake multi-database functionality.

The contract should be future-compatible without pretending that sharding already exists.

==================================================
6. MONGODB CONNECTION MANAGEMENT
==================================================

Implement a persistent MongoDB infrastructure adapter.

Requirements:

- connection reuse/pooling
- no new connection per request
- controlled lifecycle
- safe startup/shutdown
- connection failure handling
- timeout configuration
- no credential logging
- no URI logging

Use the MongoDB driver or existing project-standard Mongo integration.

Do NOT add Mongoose if it is not already part of the architecture.

Prefer the official MongoDB driver for infrastructure unless an existing project abstraction explicitly requires otherwise.

==================================================
7. CONNECTION CACHE
==================================================

If multiple tenants use different physical Mongo databases, infrastructure must not create a new Mongo connection for every request.

Use a controlled connection/client cache where appropriate.

The cache key must represent the physical storage target, not arbitrary client input.

The cache must not leak credentials.

Do not create an unbounded cache.

If the current project architecture cannot safely support a connection cache yet, implement the smallest bounded infrastructure needed and document the limitation.

Do not create a memory leak disguised as a connection manager.

==================================================
8. STORAGE RESOLUTION FLOW
==================================================

The runtime flow must be:

1. Request authenticated.
2. TenantAuthorization establishes TrustedTenantContext.
3. Patient repository requests logical tenant storage.
4. Tenant Storage Resolver looks up registry metadata.
5. Infrastructure resolves the active physical storage target.
6. Mongo infrastructure obtains/reuses the appropriate connection.
7. Patient repository performs the operation inside that tenant's storage.
8. Response returns only domain data.

The client must NEVER participate in steps 4–6.

No client parameter may select:

- database
- collection
- Mongo URI
- storage target
- connection

==================================================
9. FAIL-CLOSED BEHAVIOR
==================================================

The following must fail safely:

- tenant has no storage registry
- registry entry inactive
- no active physical target
- storage target invalid
- Mongo connection failure
- Mongo authentication failure
- database unavailable
- storage resolution failure
- unknown tenant storage

Never fall back to:

- central Prisma Patient
- another tenant's database
- default database
- localhost database
- arbitrary Mongo database
- development memory in staging/production

Development memory may remain only as an explicitly configured development adapter if the project architecture still requires it.

It must NEVER activate automatically in staging or production.
