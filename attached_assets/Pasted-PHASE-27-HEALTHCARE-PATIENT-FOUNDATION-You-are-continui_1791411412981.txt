PHASE OBJECTIVE
==================================================

Create the foundational Tenant Patient domain.

A Patient represents a person receiving healthcare services inside a specific Tenant.

The Patient is TENANT-SCOPED.

A patient in Tenant A must be completely isolated from Tenant B.

This phase establishes only the patient's identity/demographic foundation.

The Patient must NOT yet participate in:
- appointments
- visits
- encounters
- medical records
- prescriptions
- billing
- insurance
- payments
- service booking
- scheduling
- notifications
- clinical workflows

==================================================

Platform User
Tenant Membership
Staff

Patient

A Patient does NOT require:

For this phase, implement the Patient foundation using the same persistence architecture already used by the current healthcare catalog foundations.

Do not create a separate patient database.

The Patient model must remain explicitly tenant-scoped so that later migration/expansion of healthcare operational data can preserve the established tenant storage boundary.

==================================================
4. PATIENT NUMBER
==================================================

Patient number is a TENANT-SCOPED business identifier.

It must NOT be globally unique.

Example:

Tenant A:
PAT-000001

Tenant B:
PAT-000001

Both are valid.

The database uniqueness rule must therefore be:

tenantId + patientNumber

Do NOT use global uniqueness.

Do NOT expose database IDs as the patient's business identifier.

Do not create automatic human-readable numbering unless the repository already has an established safe numbering mechanism.

If automatic generation is implemented, it must be concurrency-safe.

If automatic generation cannot be implemented safely within this phase, make patientNumber explicitly supplied and validated, and report that decision.

Never implement a naive:
MAX(patientNumber) + 1

approach.
