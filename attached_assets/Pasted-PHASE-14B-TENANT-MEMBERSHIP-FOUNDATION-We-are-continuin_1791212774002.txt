==================================================
1. ARCHITECTURAL PRINCIPLE
==================================================

A PlatformUser does NOT automatically have access to every Tenant.

A Tenant ID does NOT grant access.

Membership is the explicit relationship between:

Platform Identity
and
Tenant.

The future authorization chain is:

Platform Authentication
→ Tenant Membership
→ Tenant Role
→ Tenant Permission
→ Subscription Entitlement
→ Business Operation

Only implement the Membership layer in this phase.

==================================================
2. MEMBERSHIP MODEL
==================================================

Inspect the existing Prisma schema and Phase 14A Tenant model.

Create a central Prisma model for TenantMembership.

Use the existing project naming and identifier conventions.

At minimum the model should support:

- id
- tenantId
- platformUserId
- membership status
- createdAt
- updatedAt
- lifecycle timestamps where justified

Use explicit enums rather than arbitrary strings.

Design lifecycle states carefully.

At minimum evaluate states such as:

- INVITED
- ACTIVE
- SUSPENDED
- REMOVED

Only include states that are actually justified.

Do not create unnecessary future states.

==================================================
3. RELATIONSHIPS
==================================================

TenantMembership must have proper relations to:

- PlatformUser
- Tenant

Inspect existing Prisma relation conventions before implementing.

Define appropriate:

- foreign keys
- indexes
- uniqueness constraints

A user should not accidentally have multiple active memberships representing the same logical membership.

Design uniqueness carefully.

Do not assume membership role belongs here yet.

Roles will be implemented separately in Phase 14C.

==================================================
4. MEMBERSHIP LIFECYCLE
==================================================

Implement explicit lifecycle rules.

Examples:

INVITED
→ ACTIVE

ACTIVE
→ SUSPENDED

ACTIVE
→ REMOVED

SUSPENDED
→ ACTIVE

Define only transitions that make business sense.

Invalid transitions must fail closed.

Do not allow:

REMOVED
→ ACTIVE

unless there is a deliberate reactivation model already justified by the architecture.

If reactivation is required, define it explicitly rather than accidentally allowing arbitrary status mutation.

Do not allow clients to directly set arbitrary membership status.

==================================================
5. MEMBERSHIP SERVICE
==================================================

Create a TenantMembershipService.

Business rules belong here.

The service should support the minimum operations required for this phase.

At minimum consider:

- create/invite membership
- activate membership
- suspend membership
- remove membership

Do not build a large generic CRUD service.

Validate:

- tenant exists
- platform user exists
- membership uniqueness
- valid lifecycle transition
- required inputs

Do not create a membership for a nonexistent tenant/user.

==================================================
6. REPOSITORY
==================================================

Create a TenantMembershipRepository.

Follow:

Controller
→ Service/Policy
→ Repository
→ Prisma

Controllers must not access Prisma.

Repository operations should be explicit.

Avoid exposing unrestricted Prisma access.

Future tenant-owned repositories will use TrustedTenantContext.

Membership itself is central platform/SaaS metadata, so do not put it into MongoDB.

==================================================
7. AUTHORIZATION BOUNDARY
==================================================

DO NOT implement Tenant Authorization yet.

However, membership management itself is a privileged platform operation.

Inspect the existing platform permission model.

Use existing appropriate platform authorization where possible.

Do NOT invent a large new permission taxonomy.

If new platform permissions are genuinely required, explain why before adding them and keep them narrowly scoped.

Never allow:

- request body to choose the acting user
- request body to grant itself membership
- client-provided role IDs
- client-provided permission IDs
- tenant ID alone to authorize the operation

Actor identity must come from trusted authenticated server context.

==================================================
8. INVITATION DESIGN
==================================================

This phase may create the membership foundation for invitations, but do NOT implement email/SMS/WhatsApp invitation delivery.

Do not build an invitation-token system unless the existing architecture already requires it.

If membership creation represents an administrative invitation, model the membership state accordingly.

Communication channels belong to a later phase.

==================================================
9. MEMBERSHIP ACCESS RULE
==================================================

Establish the invariant:

A PlatformUser can access tenant-scoped functionality only if an appropriate active membership exists.

Do NOT implement the full TenantAuthorizationGuard yet.

However, create tests and contracts that establish this invariant.

Do not treat:

- tenant ID
- platform user ID
- UUID
- hostname
- slug

as sufficient authorization.

==================================================
10. API
==================================================

If HTTP endpoints are needed, follow the existing API convention:

/api/v1/...

Membership administration endpoints must NOT be public.

Use the existing:

PlatformAuthGuard
+
PlatformAuthorizationGuard

where applicable.

Do not expose tenant membership management to arbitrary authenticated users.

Do not create public tenant APIs.

Keep the endpoints minimal.

==================================================
11. AUDIT / SECURITY
==================================================

Integrate membership lifecycle changes with the existing Platform Audit/Security foundation.

At minimum consider audit events for:

- membership created/invited
- membership activated
- membership suspended
- membership removed

Use trusted authenticated actor context.

Do not store:

- passwords
- tokens
- cookies
- secrets
- credentials
- database URLs

in audit metadata.

Do not allow the request body to define audit actor identity.

Do not create a new audit system.

Use the existing PlatformSecurity/Audit infrastructure.

==================================================
12. SECURITY REQUIREMENTS
==================================================

Review specifically for:

- IDOR
- privilege escalation
- self-membership escalation
- unauthorized membership creation
- unauthorized membership status changes
- client-controlled actor IDs
- client-controlled role IDs
- duplicate membership creation
- cross-tenant membership confusion
- mass assignment
- arbitrary status mutation

Important:

Membership establishes relationship.

Membership does NOT establish permissions.

Do not add role authorization into this phase.

==================================================
13. TENANT ISOLATION
==================================================

Membership records are central SaaS metadata.

Do not store them in tenant MongoDB.

The membership must always explicitly reference the Tenant.

Do not create any mechanism where:

Tenant A membership
can accidentally be interpreted as
Tenant B membership.

Use composite uniqueness/indexing where appropriate.
