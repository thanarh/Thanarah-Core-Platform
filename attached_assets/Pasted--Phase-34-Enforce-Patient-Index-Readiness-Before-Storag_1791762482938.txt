# Phase 34 — Enforce Patient Index Readiness Before Storage Activation

Implement the missing activation gate in Thanarah. This is an implementation task, not another audit.

## 1. Inspect the existing architecture first

Inspect:
- `src/tenant/tenant-storage.registry.ts`
- `src/tenant/mongo-tenant-patient.storage.ts`
- `src/tenant/tenant-mongo-client.manager.ts`
- `test/tenant-storage.registry.spec.ts`
- `test/mongo-tenant-patient.storage.spec.ts`
- Existing dependency injection, target resolution, transaction, and activation conventions.

Use the actual repository interfaces. Do not invent a parallel storage abstraction.

## 2. Required invariant

A tenant storage target must never become active for Patient writes until all required Patient indexes have been successfully provisioned and verified for that exact target.

Integrate `ensureIndexesForTarget` through an appropriate application-service boundary. Do not put MongoDB operations directly into controllers or make Prisma repositories responsible for MongoDB operations.

The gate must:
- Resolve the intended target using trusted server-side identifiers.
- Provision and verify required indexes on the intended target.
- Activate the target only after verification succeeds.
- Leave the target inactive if connectivity, provisioning, or verification fails.
- Preserve existing active-primary conflict behavior.
- Never accept client-supplied connection strings, physical database names, or cluster identifiers as trusted routing instructions.
- Preserve all current Patient-number and duplicate-protection index definitions.
- Never merge, delete, or rewrite Patient records as part of activation.

## 3. Concurrency and consistency

Review how the existing Prisma transaction protects registry state.

Prevent concurrent activation attempts from violating the existing single-active-primary invariant. Do not assume that a Prisma transaction can atomically include MongoDB index creation.

If a race exists between index verification and activation, design the narrowest safe solution supported by the current architecture. Document any residual race or limitation explicitly; do not claim a stronger guarantee than the implementation provides.

Do not deactivate an existing target or change the authoritative target before the new target has passed all required checks.

## 4. Focused tests

Add or update tests for:
- Successful activation after index verification.
- Index-creation failure leaves the target inactive.
- Index-verification failure leaves the target inactive.
- MongoDB unavailable leaves the target inactive.
- Existing duplicate data that prevents unique-index creation leaves the target inactive.
- Existing active-primary conflicts remain enforced.
- Concurrent activation attempts preserve the existing invariant.
- Failed activation does not modify or delete Patient records.
- Existing Patient duplicate-protection behavior remains unchanged.

Use mocks for the focused unit tests. Do not run the container-backed Phase 30 integration suite without first reviewing its setup and obtaining explicit approval for any destructive or migration-related test operations.

## 5. Restrictions

- Do not connect to production.
- Do not inspect or print credentials.
- Do not implement cluster rotation, automatic provisioning of Atlas projects/clusters, data migration, archive routing, or sharding.
- Do not weaken unique indexes or duplicate checks.
- Do not change central MySQL/MariaDB into Patient-record storage.
- Do not stage or commit changes.
- Do not use `--no-verify`.

## 6. Validation and report

Run the three focused spec files:
- `test/tenant-storage.registry.spec.ts`
- `test/mongo-tenant-patient.storage.spec.ts`
- `test/tenant-mongo-client.manager.spec.ts`

Also run relevant build, type-check, lint, formatting, and `git diff --check` commands available in the repository.

Report:
- Exact files changed.
- How the activation gate works.
- Test commands and actual results.
- Concurrency guarantees and remaining limitations.
- Confirmation that no production connection was made.
- Final `git status --short`.

Stop after reporting. Do not proceed to another phase.
