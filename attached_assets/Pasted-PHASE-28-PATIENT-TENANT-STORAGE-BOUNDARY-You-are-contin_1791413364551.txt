==================================================
PHASE OBJECTIVE
==================================================

Move the Patient persistence boundary from direct central Prisma/MySQL persistence toward the established Tenant Storage architecture.

The end state must make Patient persistence explicitly tenant-storage based.

The application/service layer must not know:
- MongoDB connection strings
- MongoDB database names
- physical database identifiers
- credentials
- tenant database URLs

Those details belong to the Tenant Storage infrastructure layer.

The Patient domain must depend on a repository/storage contract, not directly on Prisma.

==================================================

Before writing code, inspect the repository for the existing architecture established for:

- TrustedTenantContext
- Tenant Storage Resolver
- Tenant DB Registry
- tenant-scoped repositories
- storage abstractions
- MongoDB/Mongoose remnants
- any existing tenant storage interfaces
- central Prisma repository conventions

==================================================
2. HARD ARCHITECTURAL BOUNDARY
==================================================

Patient code must follow:

Controller
  ↓

  ↓
Patient Repository Contract
  ↓

  ↓

The Patient Service must NOT:

- import PrismaClient directly
- access MongoClient directly
- access Mongoose directly
- construct MongoDB database names
- read tenant database URLs
- read database credentials
- select a physical tenant database

The repository implementation is responsible for storage.

==================================================
3. CENTRAL DATABASE ROLE
==================================================

The central Prisma/MySQL database must NOT remain the authoritative persistence location for Patient records after this phase.

Do not create a second central Patient table.

Do not duplicate Patient records in both central MySQL and tenant MongoDB as permanent runtime state.

Do not use MySQL as a fallback if tenant storage is unavailable.

Fail closed.

==================================================
4. PATIENT REPOSITORY CONTRACT
==================================================

Define or adapt a Patient repository contract that is explicitly tenant-scoped.

The repository must require TrustedTenantContext or an equivalent server-generated tenant storage context according to the existing architecture.

Do not allow repository callers to provide:

- arbitrary tenantId
- database name
- Mongo URI
- physical database ID
- connection string

The repository must derive storage from trusted tenant context.

Conceptually:

PatientService
  → PatientRepository
      → TenantStorageResolver
          → Tenant database

Do not expose physical storage identifiers to the domain layer.

==================================================
5. STORAGE RESOLUTION
==================================================

Tenant storage resolution must be fail-closed.

For a valid tenant:

1. TrustedTenantContext establishes tenant identity.
2. Tenant Storage Resolver obtains the tenant's storage registry information.
3. Infrastructure resolves the appropriate physical database.
4. Patient repository operates only inside that resolved tenant storage.

If storage resolution fails:

- do not silently fall back to central MySQL
- do not guess a database
- do not create a new database automatically
- do not continue against another tenant
- return the project's established safe infrastructure/storage error

Do not expose:
- MongoDB URI
- database name
- internal storage IDs
- connection credentials

to API responses.

==================================================
6. MULTI-PHYSICAL-DATABASE SUPPORT
==================================================

The architecture must remain compatible with the permanent requirement that one logical Tenant may eventually use multiple physical databases.

Do NOT hard-code:

Tenant → exactly one Mongo database

The abstraction should allow:

Tenant
  ↓
logical tenant storage
  ↓
one or more physical database targets

For Phase 28:

You do NOT need to implement sharding, partitioning, automatic capacity management, or rebalancing.

But do not design the repository contract in a way that makes those future capabilities impossible.

The Patient repository should operate against a logical tenant storage context, not a raw database name.
