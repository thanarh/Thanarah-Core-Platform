PHASE 24 — DOCTOR PROFESSIONAL PROFILE FOUNDATION

You are continuing the Thanarah production SaaS architecture.

This is a REAL commercial multi-tenant healthcare SaaS system.
Do NOT treat this as a prototype.

Implement ONLY Phase 24.
Do not start Phase 25.

==================================================
1. PHASE GOAL
==================================================

Build the minimal professional profile foundation for the existing Doctor entity.

Phase 23 established:

Platform User
    ↓
Tenant Membership
    ↓
Staff
    ↓
Doctor
    ├── Department assignments
    └── Specialty assignments

Phase 24 adds professional profile metadata to Doctor.

The goal is to represent professional information that is useful for administration and future healthcare workflows.

This phase is NOT a licensing/verification system.

==================================================
2. IMPORTANT ARCHITECTURAL BOUNDARY
==================================================

Doctor already exists.

DO NOT create another Doctor model.

Do NOT create another Staff model.

Do NOT create another User model.

Do NOT create another authentication identity.

The professional profile belongs to the existing Doctor.

Preferred conceptual structure:

Doctor
    └── Professional Profile

If the current architecture can safely keep these fields directly on Doctor without creating an excessive separate table, prefer the simpler design.

Only create a separate DoctorProfessionalProfile model if the existing architecture or data lifecycle genuinely benefits from separation.

Do not create abstractions merely for theoretical future use.

==================================================
6. RECOMMENDED PROFILE FIELDS
==================================================

Before implementation, determine the minimum useful profile.

A reasonable foundation may contain:

displayName
professionalTitle
professionalCode
bio

Optionally:

yearsOfExperience

But do not add fields merely because they are common in healthcare systems.

Every field must have:

- clear purpose
- validation
- API behavior
- OpenAPI representation
- test coverage

If the existing specification does not justify a field, leave it out.

==================================================
7. TENANT OWNERSHIP
==================================================

Professional profile belongs to Doctor.

Doctor already belongs to Staff and Tenant.

Do not allow changing:

- tenantId
- staffId
- membershipId

through professional profile updates.

TrustedTenantContext remains authoritative.

Cross-tenant profile access must fail.

==================================================
8. DOCTOR STATUS
==================================================

Professional profile does not replace Doctor lifecycle.

Existing Doctor lifecycle remains:

ACTIVE
SUSPENDED
DEACTIVATED

Professional profile updates must not automatically activate/deactivate Doctor.

Do not create a second profile lifecycle.

If Doctor is DEACTIVATED, profile data remains available for administrative/history purposes according to existing read conventions.

==================================================
9. STAFF STATUS
==================================================

Do not bypass Staff lifecycle.

Doctor professional profile updates require the existing Doctor/Staff authorization path.

A SUSPENDED or DEACTIVATED Staff member must not become operational merely because profile data is updated.

Do not modify Staff status from the Doctor profile API.

==================================================
10. PROFESSIONAL TITLE
==================================================

If implemented, professionalTitle is descriptive metadata.

Examples:

- Consultant
- Specialist
- General Practitioner

Do NOT turn professionalTitle into:

- Role
- Permission
- Specialty
- Department

It is display/profile metadata only.

Do not infer authorization from it.

==================================================
11. PROFESSIONAL CODE
==================================================

If implemented, professionalCode must have clear tenant scope.

Do not make it globally unique unless existing architecture explicitly requires global uniqueness.

Preferred:

unique within tenant

If uniqueness requires Doctor + Tenant composite constraints, implement them at database level where practical.

Do not use the professional code as authentication.

Do not use it as a permission identifier.

==================================================
12. BIO
==================================================

If a biography/about field is implemented:

- validate maximum length
- normalize safely
- do not execute/render HTML
- do not accept arbitrary unsafe markup
- preserve plain text semantics

Do not create a rich-text editor backend.

Do not add HTML sanitization infrastructure unless required by the existing project.

==================================================
13. YEARS OF EXPERIENCE
==================================================

If implemented:

- integer only
- non-negative
- reasonable maximum
- reject decimals
- reject negative values
- reject unsafe numeric values

Do not calculate experience automatically from employment records.

This is a declared profile value.

Do not create an employment-history subsystem.

==================================================
14. API DESIGN
==================================================

Use the existing Doctor API conventions.

Prefer extending existing Doctor DTOs when that is architecturally cleaner.

The goal is one coherent Doctor API, not multiple competing representations.

Inspect the existing implementation first.

==================================================
16. AUTHORIZATION
==================================================

Use existing doctor authorization.

Do NOT create:

DoctorProfileGuard
DoctorProfileAuthorizationGuard

unless a very narrow reusable policy is genuinely necessary.

Existing permission convention should remain authoritative.

If:

doctor.read
doctor.manage

already exist, reuse them.

Profile reads require the appropriate read permission.

Profile mutations require the appropriate manage permission.

Do not automatically grant doctor.manage to doctors themselves.

A Doctor profile does NOT imply permission to edit itself.

Authorization remains role-based.
