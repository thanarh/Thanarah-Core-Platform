PHASE 15 — SaaS PLANS FOUNDATION

==================================================
PRIMARY OBJECTIVE
==================================================

Introduce the central SaaS Plan foundation.

This phase establishes the architecture required to distinguish:

1. Authentication
2. Authorization
3. Subscription
4. Entitlement
5. Usage limits

These concepts MUST remain separate.

The target conceptual flow is:

Authentication
    ↓
Tenant Membership
    ↓
Tenant Authorization
    ↓
Subscription Status
    ↓
Plan
    ↓
Entitlement
    ↓
Usage Limit
    ↓
Business Operation

Do NOT implement active subscriptions yet.

Do NOT implement billing yet.

Do NOT implement payments yet.

Do NOT implement usage metering yet.

==================================================
1. ARCHITECTURAL BOUNDARY
==================================================

Plans are PLATFORM/SaaS metadata.

Plans belong in the CENTRAL PLATFORM DATABASE.

Use Prisma + MySQL/MariaDB.

Do NOT put Plan data into tenant MongoDB.

Conceptually:

Platform
 ├── Users
 ├── Roles
 ├── Permissions
 ├── Tenants
 ├── Plans
 ├── Features
 └── future Subscriptions
        ↓
Tenant operational data remains separate.

==================================================
2. PLAN VS SUBSCRIPTION
==================================================

This distinction is mandatory.

A Plan is a reusable definition.

A Subscription is a tenant-specific commercial assignment to a Plan.

Examples:

Plan:
PRO

Subscription:
Tenant A subscribed to PRO from date X to date Y.

DO NOT create Subscription in Phase 15.

Do not put:

tenantId

inside Plan.

A Plan is not owned by a Tenant.

Multiple Tenants will eventually reference the same Plan through Subscriptions.

==================================================
3. PLAN MODEL
==================================================

Create a SaaS Plan model using the existing Prisma naming conventions.

At minimum evaluate:

- id
- key/code
- name
- description
- status
- createdAt
- updatedAt

Keep it intentionally small.

Do NOT add billing fields yet.

Do NOT add:

- price
- currency
- billingInterval
- trialDays
- paymentProviderId
- Stripe IDs
- PayPal IDs
- invoice settings
- tax settings

Those belong to later commercial/billing phases.

If a future billing layer needs them, it can be introduced without corrupting this foundation.

==================================================
4. PLAN KEY
==================================================

Plans need a stable machine-readable identifier.

Example:

FREE
STARTER
PRO
ENTERPRISE

Use the project's established naming convention.

The key/code must be:

- unique
- stable
- server-controlled
- safe for internal references

Do not use display name as the primary machine identifier.

Do not allow arbitrary tenant users to change the key.

==================================================
5. PLAN NAME
==================================================

Plan name is presentation/business metadata.

It may be changed according to platform administration rules.

Do not use name as a foreign key.

Do not make authorization decisions based on display name.

==================================================
6. PLAN STATUS
==================================================

Introduce a clear Plan lifecycle.

Recommended:

ACTIVE
INACTIVE
ARCHIVED

Inspect existing project lifecycle conventions and use consistent naming if an equivalent already exists.

Important:

An inactive/archived Plan must not be treated as an available plan for future subscriptions.

However:

Do NOT implement subscription behavior yet because subscriptions are out of scope.

Do not physically delete plans.

Use lifecycle/status instead.

Define valid transitions.

Do not invent unnecessary lifecycle complexity.

==================================================
7. FEATURE / ENTITLEMENT DEFINITION
==================================================

Introduce a reusable SaaS Feature definition.

A Feature represents a capability that can eventually be granted by a Plan.

Examples:

PATIENTS
APPOINTMENTS
DOCTORS
REPORTS
WHATSAPP
VOICE_AI
ADVANCED_ANALYTICS

These are examples only.

Do not automatically add every future feature to the database.

Keep the initial feature catalog minimal.

The feature definition must be separate from:

Tenant permissions.

This is critical.

Tenant Permission answers:

"Can this authenticated tenant member perform this operation?"

Entitlement answers:

"Does this tenant's commercial plan allow this capability?"

They must never be merged.

==================================================
8. PERMISSION VS ENTITLEMENT
==================================================

Document this exact distinction.

Example:

A tenant may have:

Tenant Permission:
appointments.create

but if the tenant's commercial entitlement does not include appointments:

the business operation should eventually be blocked by entitlement.

Conversely:

A plan may include appointments,

but a receptionist without:

appointments.create

must still be denied by authorization.

Therefore:

Authorization AND Entitlement

are both required before a future business operation proceeds.

Do NOT implement this combined runtime gate in Phase 15.

Only establish the foundation.
