# Phase 36 — Harden Tenant Patient Index Verification

## Objective

Correct the documented gaps in the tenant Patient index-readiness verifier, with focused implementation, regression coverage, and a final consolidated review.

The current audit identified two issues in `src/tenant/mongo-tenant-patient.storage.ts`:

1. `sameIndexKey` compares compound-index fields without preserving field order.
2. Patient-number index verification does not validate the expected collation.

Resolve these issues based on the actual index definitions and supported MongoDB behavior. Do not broaden the task into infrastructure selection or deployment redesign.

## Stage 1 — Establish the baseline

Inspect the current working tree, `HEAD`, and all pending changes before editing.

Preserve the existing documentation modifications in:
- `TENANT_MONGODB_DEPLOYMENT_DECISION.md`
- `replit.md`

Do not overwrite, revert, stage, or commit those changes.

Inspect the current index definitions, provisioning logic, verifier, activation service, and existing MongoDB integration tests.

## Stage 2 — Define exact verification semantics

Derive expected verification behavior from the actual index definitions.

For every index covered by the verifier, determine:
- Expected index name.
- Ordered compound key fields and directions.
- Uniqueness.
- Partial-filter expression, where applicable.
- Collation, including whether the expected behavior is explicit or relies on MongoDB's default simple collation.
- Any other index property necessary to guarantee the existing write-enforcement behavior.

Do not assume every created index is currently verified.

Do not silently change the duplicate-matching rules, index names, normalization semantics, or partial-filter semantics.

## Stage 3 — Fix compound-key verification

Update the comparison logic so compound-key field order is verified exactly as required by the expected index definition.

Ensure that:
- Reordered compound keys are rejected.
- Missing or extra key fields are rejected.
- Incorrect key directions are rejected.
- Correct index definitions continue to pass.

Avoid broad refactoring unrelated to index readiness.

## Stage 4 — Fix Patient-number collation verification

Determine the intended Patient-number index collation from the actual index definition and write semantics.

Implement a precise check that distinguishes the expected collation from a missing or incompatible collation.

Account explicitly for MongoDB's representation of the default simple collation. Do not treat omitted metadata as proof of an incompatible index without checking the documented driver/server behavior.

Do not change the Patient-number uniqueness rule or existing conflict precedence.

## Stage 5 — Regression tests

Add focused tests for:
- Correct compound-key order.
- Incorrect compound-key order.
- Missing and extra compound-key fields.
- Incorrect key directions.
- Correct Patient-number collation.
- Missing or incompatible Patient-number collation.
- Missing indexes.
- Incorrect uniqueness and partial-filter properties where relevant.
- Fail-closed Patient writes when required verification fails.
- Activation and primary assignment refusing targets when provisioning/verification fails.

Use the existing test conventions and fixtures.

If integration tests require a MongoDB server, use only the existing disposable non-production test setup. Never connect to production.

## Stage 6 — Compatibility review

- What remains unverified until the intended deployment profile is approved.
