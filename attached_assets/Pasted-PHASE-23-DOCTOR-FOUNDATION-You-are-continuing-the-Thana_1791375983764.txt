PHASE 23 — DOCTOR FOUNDATION

You are continuing the Thanarah production SaaS architecture.

This is a REAL commercial multi-tenant healthcare SaaS system.
Do NOT treat this as a prototype.

Implement ONLY Phase 23.
Do not start Phase 24.

==================================================
1. PHASE GOAL
==================================================

Create the foundational Doctor domain.

A Doctor is a healthcare-specific profile built on an existing Staff record.

The intended identity chain is:

Platform User
    ↓
Tenant Membership
    ↓
Staff
    ↓
Doctor Profile
    ├── Department relationship
    └── Specialty relationship
    ↓
Future healthcare operations

IMPORTANT:

Doctor is NOT:
- a Platform User
- a Tenant Membership
- a Staff replacement
- a Tenant Role
- a Permission
- an Entitlement
- a Facility
- a Branch

Doctor is a specialized healthcare profile associated with an existing Staff identity.

==================================================
2. DATABASE BOUNDARY
==================================================

Phase 23 uses the CENTRAL Prisma database for:

- Doctor administrative/profile metadata
- Department references
- Specialty references
- Tenant ownership metadata

Do NOT create MongoDB healthcare collections in this phase.

MongoDB remains reserved for future tenant operational/clinical data.

Do NOT move clinical records, encounters, prescriptions, or patient data into Prisma.

==================================================
5. ONE DOCTOR PROFILE PER STAFF
==================================================

A Staff member may have at most one Doctor profile per tenant.

Prefer a database uniqueness constraint:

(staffId)

or the appropriate tenant-qualified equivalent if required by the existing schema.

Do NOT allow:

Staff A
→ Doctor A
→ Doctor B

inside the same tenant.

Creation must reject duplicate doctor profiles.

==================================================
6. TENANT INTEGRITY
==================================================

Doctor, Staff, Department, and Specialty must all belong to the same tenant.

Never trust client-provided tenant ownership.

If Doctor has tenantId, enforce:

Doctor.tenantId == Staff.tenantId

If Doctor references Department:

Doctor.tenantId == Department.tenantId

If Doctor references Specialty:

Doctor.tenantId == Specialty.tenantId

Use database composite foreign keys where practical.

Do not create relationships that can drift across tenants.

Cross-tenant relationships must fail closed.

==================================================
7. DOCTOR STATUS
==================================================

Use a lifecycle consistent with Staff.

Preferred:

ACTIVE
SUSPENDED
DEACTIVATED

Rules:

ACTIVE → SUSPENDED
ACTIVE → DEACTIVATED

SUSPENDED → ACTIVE
SUSPENDED → DEACTIVATED

DEACTIVATED is terminal.

Do not hard-delete Doctor records.

Do not silently reactivate DEACTIVATED doctors.

Use the project's existing same-state/idempotency conventions.

==================================================
8. STAFF ELIGIBILITY
==================================================

Doctor creation requires:

- authenticated actor
- valid TrustedTenantContext
- active tenant
- existing Staff
- Staff belongs to current tenant
- Staff is ACTIVE
- Staff membership remains valid
- Staff is not already associated with another Doctor profile

A SUSPENDED or DEACTIVATED Staff member must not be converted into an active Doctor profile.

Do not bypass Staff lifecycle.

==================================================
9. STAFF / DOCTOR LIFECYCLE RELATIONSHIP
==================================================

Doctor is subordinate to Staff.

If Staff becomes:

SUSPENDED
or
DEACTIVATED

Doctor must not be considered operationally active.

Do NOT automatically delete Doctor.

Do NOT silently rewrite Doctor status unless the existing lifecycle architecture explicitly requires it.

Instead, define and test effective Doctor availability using:

Staff ACTIVE
AND
Doctor ACTIVE

This prevents a Doctor profile from bypassing Staff lifecycle.

If the project already has a standardized effective-state pattern, reuse it.

==================================================
10. DEPARTMENT RELATIONSHIP
==================================================

Phase 22 intentionally created independent Department and Specialty catalogs.

Phase 23 may now connect Doctor to those catalogs.

Do NOT store department IDs as JSON arrays.

A Doctor may potentially belong to multiple departments.

Therefore inspect the product architecture and implement the smallest relational structure that supports the intended multi-department model.

Preferred if multiple departments are supported:

DoctorDepartmentAssignment

Conceptually:

- doctorId
- departmentId
- tenant-qualified integrity
- createdAt

Unique:

(doctorId, departmentId)

If the current architecture/specification clearly establishes exactly one primary department, do not invent multi-department behavior.

Inspect first and document the decision.

==================================================
11. SPECIALTY RELATIONSHIP

Prefer an explicit relational assignment model if multiple specialties are supported.

Conceptually:

DoctorSpecialtyAssignment

- doctorId
- specialtyId

- createdAt

Unique:

(doctorId, specialtyId)

Do NOT create duplicate specialty definitions.

Reuse the tenant Specialty catalog from Phase 22.

==================================================
12. IMPORTANT: DEPARTMENT VS SPECIALTY
==================================================

Do not confuse:

Department
with
Specialty.

Example:

Department:
Cardiology Department

Specialty:
Interventional Cardiology

A Doctor may be associated with one or more departments and one or more specialties according to the product model.

Do not create automatic Department creation when assigning a Specialty.

Do not automatically infer one from the other.

Both references must be explicit.
