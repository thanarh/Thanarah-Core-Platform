PHASE 14E — FACILITY FOUNDATION

==================================================
PRIMARY OBJECTIVE
==================================================

Introduce the Facility layer beneath Tenant/Organization.

The architectural hierarchy must now be:

Platform
  ↓
Tenant / Organization
  ↓
Facility
  ↓
Future Branch
  ↓
Future Staff / Doctors / Healthcare Operations

Important:

Tenant/Organization is NOT a Facility.

A Tenant may operate one or more Facilities.

A Facility belongs to exactly one Tenant.

Do not collapse Tenant and Facility into one entity.

==================================================
STRICT SCOPE
==================================================

Implement only the Facility foundation:

- Facility domain model
- Facility repository
- Facility service
- Facility lifecycle/status
- Tenant-scoped Facility authorization
- Facility CRUD foundation
- Facility audit integration
- Facility tests
- Documentation
- Prisma migration if required

Do NOT implement:

- Branch
- Staff
- Doctors
- Patients
- Departments

==================================================
1. DOMAIN MODEL
==================================================

Create a Facility model in the CENTRAL PLATFORM DATABASE.

Facility is SaaS/platform metadata.

Do NOT put Facility into MongoDB.

Relationship:

Tenant
  1
  |
  | has many
  ↓
Facility

Every Facility must have exactly one tenantId.

A Facility must never exist without a Tenant.

Use the project's existing Prisma naming and ID conventions.

Do not introduce a second tenant identifier system.

==================================================
2. FACILITY FIELDS
==================================================

Use only fields required for a clean commercial foundation.

At minimum evaluate:

- id
- tenantId
- name
- code or slug if appropriate
- status
- createdAt
- updatedAt

Do not over-model the Facility yet.

Do NOT add:

- doctors
- staff
- departments
- medical configuration
- appointment settings
- billing settings
- insurance settings
- clinical settings

Those belong to later phases.

If using a unique facility code/slug, define its uniqueness correctly within the tenant.

A Facility identifier must not be globally unique unless there is a clear architectural reason.

Prefer tenant-scoped uniqueness.

==================================================
3. FACILITY STATUS
==================================================

Introduce an explicit Facility lifecycle.

Use a small, clear state machine.

Recommended states:

ACTIVE
SUSPENDED
DEACTIVATED

If the existing architecture has a consistent lifecycle naming convention, follow it.

Do not invent unnecessary states.

Define allowed transitions explicitly.

At minimum:

ACTIVE → SUSPENDED
ACTIVE → DEACTIVATED

SUSPENDED → ACTIVE
SUSPENDED → DEACTIVATED

DEACTIVATED should be terminal unless the existing architecture has a justified reactivation concept.

Do not physically delete a Facility as part of lifecycle management.

Status changes must be explicit.

Same-state updates should be handled consistently with existing Tenant/Membership lifecycle behavior.

==================================================
4. TENANT RELATIONSHIP
==================================================

Facility must always be tenant-scoped.

Never allow:

Facility A from Tenant A
to be accessed through
Tenant B context.

Every repository operation must carry trusted tenant scope.

Do not create repository methods such as:

findFacilityById(id)

if they allow an unscoped tenant lookup.

Prefer:

findById(tenantContext, facilityId)

or an equivalent tenant-scoped repository contract.

The exact implementation may follow existing project conventions.

==================================================
5. TRUSTED TENANT CONTEXT
==================================================

Reuse the Phase 14D TrustedTenantContext.

Do not create another context abstraction.

Facility operations must require:

Authenticated User
+
Trusted Tenant Context
+
Tenant Authorization

The request's tenantId is never sufficient by itself.

The tenant context must already have been validated.

Do not trust:

- request body tenantId
- query tenantId
- arbitrary headers
- client-provided tenant role
- client-provided permissions

==================================================
6. FACILITY AUTHORIZATION
==================================================

Do not create a completely new authorization architecture.

Reuse TenantAuthorizationGuard and the Phase 14D tenant permission system.

Define facility permissions only if the current permission architecture requires them.

If new permissions are needed, keep them clearly within the tenant permission namespace.

Recommended conceptual permissions:

facilities.read
facilities.create
facilities.update
facilities.suspend
facilities.activate
facilities.deactivate

However:

Before adding these exact permissions, inspect the existing Phase 14C permission model and naming conventions.

Follow the established conventions instead of blindly duplicating names.

Do not add platform permissions for facility operations.

Facility authorization is tenant authorization.

==================================================
7. FACILITY CRUD
==================================================

Implement the minimum professional CRUD foundation.

Required operations:

CREATE
READ LIST
READ BY ID
UPDATE
STATUS TRANSITION

Do not implement physical DELETE.

The API should remain under:

/api/v1/...

Use the existing API conventions.

Use the existing PlatformAuthGuard + TenantAuthorizationGuard architecture.

Do not create a global facility guard.

==================================================
8. CREATE FACILITY
==================================================

Creation must:

1. Authenticate the user.
2. Resolve TrustedTenantContext.
3. Verify required tenant permission.
4. Validate input.
5. Create the Facility using the tenant from trusted context.
6. Ignore any client-supplied tenantId for ownership.

The client must NOT be able to create:

{
  tenantId: "another-tenant"
}

and change ownership.

The service must always derive tenantId from TrustedTenantContext.

==================================================
9. READ FACILITIES
==================================================

List operations must be tenant-scoped.

Example conceptual request:

GET /api/v1/tenants/:tenantId/facilities

The route tenantId is only an input to trusted tenant resolution.

The repository query must still scope by the resolved tenant context.

Never return facilities belonging to another tenant.

For:

GET /api/v1/tenants/:tenantId/facilities/:facilityId

the lookup must include tenant scope.

Do not:

find Facility by ID globally
then check tenant later.

Prefer a tenant-scoped database query from the beginning.

==================================================
10. UPDATE FACILITY
==================================================

Updates must not allow changing ownership.

Do not allow:

tenantId modification.

If the client sends tenantId, ignore it or reject it according to established input validation conventions.

Do not allow status changes through a generic update endpoint if the project lifecycle convention separates status transitions.

Prefer explicit lifecycle operations.

==================================================
11. STATUS TRANSITIONS
==================================================

Implement explicit service methods for lifecycle changes.

For example:

suspendFacility()
activateFacility()
deactivateFacility()

Use the actual naming convention of the project.

Validate transitions server-side.

Do not accept:

{
  status: "ACTIVE"
}

from an untrusted client and blindly persist it.

Authorization must be checked before transition.

==================================================
12. DELETE POLICY
==================================================

Do not implement DELETE.

Healthcare SaaS data must not rely on destructive deletion as the normal Facility lifecycle.

If a Facility needs to stop operating:

use DEACTIVATED.

Do not add a DELETE endpoint merely because CRUD normally includes DELETE.

Document this decision.

==================================================
13. REPOSITORY LAYER
==================================================

Follow:

Controller
→ Tenant Authorization
→ Service
→ Facility Repository
→ Prisma
→ MySQL/MariaDB

Controllers must not access Prisma directly.

Services must not perform raw Prisma access if the existing architecture requires repositories.

Repository methods must be tenant-scoped.

No unscoped Facility repository methods.

Fail closed if TrustedTenantContext is missing.

==================================================
14. DATABASE CONSTRAINTS
==================================================

The database must enforce important invariants where practical.

At minimum:

- Facility.tenantId required.
- Tenant foreign key required.
- Appropriate index on tenantId.
- Appropriate tenant-scoped uniqueness for code/slug if introduced.
- Foreign key behavior must not allow orphaned Facilities.

Inspect existing Tenant deletion/lifecycle semantics before choosing cascade/restrict behavior.

Do NOT automatically cascade-delete Facility records from Tenant deletion.

Prefer restrictive behavior unless the existing architecture has an explicit lifecycle strategy.

==================================================
15. AUDIT

- FACILITY_CREATED
- FACILITY_UPDATED

- FACILITY_DEACTIVATED

Follow the existing audit event naming/type conventions.

Do not create a second audit system.

Tenant must come from TrustedTenantContext.

Do not record:

- passwords
- tokens
- cookies
- authorization headers
- secrets
- DATABASE_URL
- sensitive request dumps

Follow existing error conventions from Phase 14D.

==================================================
19. PLATFORM ADMIN VS TENANT MEMBER
==================================================

Keep platform and tenant authorization separate.

A Platform Administrator does not automatically become a Tenant Facility operator.

Do not silently bypass tenant membership authorization because a user has a powerful platform role.

If platform-level facility management is needed later, it should be explicitly designed as a platform operation.

This phase should implement tenant-scoped Facility management.

==================================================

==================================================

This distinction is mandatory.

Facility is a higher-level operational location/entity under a Tenant.

Branch will be introduced later.

Do NOT create Branch now.

Do not add:

to Facility.

Do not model Facility as a Branch.

Do not assume:

Tenant = Facility = Branch.

The future hierarchy is:

Tenant
  ↓
Facility
  ↓
Branch
