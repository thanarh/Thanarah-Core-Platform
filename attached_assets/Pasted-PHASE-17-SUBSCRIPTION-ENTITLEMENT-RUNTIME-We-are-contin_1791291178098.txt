PHASE 17 — SUBSCRIPTION ENTITLEMENT RUNTIME

==================================================
PRIMARY OBJECTIVE
==================================================

Create the runtime entitlement layer that answers:

"Does this Tenant's current commercial subscription permit this Feature?"

The final conceptual authorization chain becomes:

Authentication
    ↓
Tenant Membership
    ↓
Tenant Authorization
    ↓
Current Subscription
    ↓
Plan
    ↓
PlanFeature
    ↓
Feature Entitlement
    ↓
Business Operation

IMPORTANT:

Tenant Authorization and Subscription Entitlement are separate.

Authorization answers:

"Is this authenticated tenant member allowed to perform this operation?"

Entitlement answers:

"Does this tenant's current commercial plan include this capability?"

A future business operation will require BOTH.

For example:

User has:
appointments.create

BUT Tenant plan does not include:
APPOINTMENTS

→ DENY

Tenant plan includes:
APPOINTMENTS

BUT User does not have:
appointments.create

→ DENY

Both are required.

==================================================
1. ARCHITECTURAL SEPARATION
==================================================

Do NOT merge entitlement with authorization.

Keep:

TenantAuthorizationService

separate from:

TenantEntitlementService

Do not modify PlatformAuthorizationGuard to understand tenant subscriptions.

Do not make PlatformAuthorizationGuard responsible for entitlements.

Do not make TenantAuthorizationGuard responsible for subscription state.

The correct sequence for future business operations is conceptually:

PlatformAuthGuard
→ TrustedTenantContext
→ TenantAuthorization
→ TenantEntitlement
→ Business Service

Do not globally apply entitlement to every route.

==================================================
2. CURRENT SUBSCRIPTION
==================================================

Reuse the Phase 16 current-subscription service/repository.

Do NOT create a second definition of "current subscription."

Current subscription must respect the exact Phase 16 semantics:

- persisted ACTIVE state
- startsAt <= now
- endsAt null OR endsAt >= now according to the established exclusive/inclusive boundary semantics
- cancelled subscriptions are not current
- suspended subscriptions are not current
- expired subscriptions are not current
- overlapping active subscriptions are invalid
- current lookup fails closed if conflicting current records are detected

Inspect the actual Phase 16 implementation and reuse it.

Do not duplicate the logic.

==================================================
3. ENTITLEMENT RESOLUTION
==================================================

Create a dedicated TenantEntitlementService or equivalent.

Minimum conceptual operation:

hasFeature(
  trustedTenantContext,
  featureKey
)

or an equivalent strongly typed service API.

The service must:

1. Require trusted tenant context.
2. Resolve the current subscription.
3. Resolve its Plan.
4. Resolve the PlanFeature relationship.
5. Resolve the Feature.
6. Verify Feature status.
7. Return an explicit entitlement decision.

Never use:

tenantId alone

as proof of entitlement.

Never trust:

- client tenantId
- client planId
- client featureId
- client featureKey as authorization evidence
- request body entitlement flags
- query parameters
- headers
- cookies

Feature keys are identifiers for server-defined feature definitions, not client-controlled permission grants.

==================================================
4. NO SUBSCRIPTION
==================================================

Define safe behavior when a Tenant has no current subscription.

Default:

NO ACTIVE SUBSCRIPTION
→ NOT ENTITLED

Fail closed.

Do not automatically grant FREE access unless a real FREE subscription exists.

Do not invent a fallback plan.

Do not silently assign a Plan.

==================================================
5. PLAN FEATURE
==================================================

A Feature is entitled only when the current subscription's Plan has an active valid PlanFeature relationship.

Conceptually:

Current Subscription
→ Plan
→ PlanFeature
→ Feature

All relationships must be validated server-side.

Do not allow a client to submit:

{
  planId: "...",
  featureId: "..."
}

and treat that as entitlement.

The current subscription is the only source of the commercial plan.

==================================================
6. FEATURE STATUS
==================================================

Respect Feature lifecycle from Phase 15.

If Feature is inactive:

→ NOT ENTITLED

Do not delete historical PlanFeature relationships merely because a Feature becomes inactive.

Do not silently mutate Plans.

The runtime decision must fail closed.

==================================================
7. PLAN STATUS
==================================================

Respect Plan lifecycle from Phase 15.

If the current Subscription references a Plan that has later become INACTIVE or ARCHIVED:

do NOT automatically rewrite the Subscription.

For runtime entitlement:

determine a consistent safe behavior.

Preferred:

INACTIVE/ARCHIVED PLAN
→ NO ACTIVE ENTITLEMENT

unless the established architecture explicitly defines another rule.

Document the decision.

Do not create a new subscription.

Do not migrate the Tenant automatically.

==================================================
8. SUBSCRIPTION STATUS
==================================================

Only a commercially effective subscription may provide entitlement.

At minimum:

ACTIVE → eligible

SUSPENDED → not entitled

CANCELLED → not entitled

EXPIRED → not entitled

Do not treat historical subscriptions as entitlement sources.

Do not use "latest subscription" as fallback.

Do not use cancelled/expired subscriptions.

==================================================
9. ENTITLEMENT DECISION
==================================================

Do not return a vague boolean internally if more information is useful.

Prefer a structured server-side result such as conceptually:

ENTITLED
NOT_ENTITLED_NO_SUBSCRIPTION
NOT_ENTITLED_PLAN
NOT_ENTITLED_FEATURE
NOT_ENTITLED_PLAN_FEATURE
NOT_ENTITLED_SUBSCRIPTION_STATUS

Use the project's established domain-result/error conventions if they provide a better pattern.

Do not expose excessive internal information to clients.

A public API may return a stable safe error such as:

FEATURE_NOT_INCLUDED

or the project's equivalent.

==================================================
10. ENTITLEMENT ERROR
==================================================

Create a stable application/domain error for a denied entitlement.

Example conceptual behavior:

Authenticated
+
Tenant membership valid
+
Tenant permission valid
+
Feature not included in plan

→ 403

Do NOT return:

401

because the user is authenticated.

Do NOT expose:

"Your plan is PRO and missing feature X"

unless that information is intentionally part of a safe future product API.

Keep operational errors minimal.

==================================================
11. ENTITLEMENT GUARD
==================================================

If appropriate, implement a dedicated:

TenantEntitlementGuard

It must remain separate from:

PlatformAuthGuard
TenantAuthorizationGuard

It should:

1. Require authenticated request context.
2. Require trusted tenant context.
3. Read server-defined feature metadata.
4. Resolve current subscription.
5. Resolve PlanFeature.
6. Verify entitlement.
7. Fail closed.

Do NOT make it global.

Do NOT apply it automatically to every tenant route.

==================================================
12. ENTITLEMENT DECORATOR
==================================================

If the existing architecture supports route metadata, introduce a tenant-specific decorator such as:

@RequireTenantFeature("APPOINTMENTS")

or the project's equivalent.

The feature key must be defined by the server.

Do not allow:

@RequireTenantFeature(req.body.feature)

or any request-controlled feature selection.

Do not mix this metadata with:

@RequireTenantPermissions(...)

Keep them distinct.

Conceptually:

@RequireTenantPermissions("appointments.create")
@RequireTenantFeature("APPOINTMENTS")

A future route can require both.

Do NOT add a healthcare route just to demonstrate this.
