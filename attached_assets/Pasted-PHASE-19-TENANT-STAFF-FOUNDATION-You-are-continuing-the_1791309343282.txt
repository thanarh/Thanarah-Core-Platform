You are continuing the Thanarah production SaaS architecture.

This is a REAL commercial multi-tenant healthcare SaaS system.

==================================================

Thanarah has two persistence domains:

A) CENTRAL PLATFORM DATABASE
Prisma 6 + MySQL/MariaDB.

Used for:
- Platform users / global identities
- Authentication
- Platform roles and permissions
- Tenants
- Tenant memberships
- Tenant roles and permissions
- Facilities
- Branches
- Plans
- Features
- Plan features
- Subscriptions
- Entitlement configuration
- Usage/quota definitions
- SaaS/platform metadata
- Audit/security metadata
- Future staff identity/administrative metadata

B) TENANT OPERATIONAL DATABASES
MongoDB.

Used later for tenant healthcare/operational data such as:
- Patients
- Doctors' clinical data
- Appointments
- Visits/encounters
- Medical records
- Clinical notes
- Prescriptions
- Documents
- Billing
- Insurance
- Notifications
- Other operational healthcare data

DO NOT move tenant healthcare data into the central Prisma database.

Phase 19 must remain on the CENTRAL DATABASE only.

==================================================
2. EXISTING IDENTITY MODEL
==================================================

The system already has:

Global Platform User
    ↓
Tenant Membership
    ↓
Tenant authorization
    ↓
Facility / Branch scope
    ↓
Business operations

A Platform User is NOT automatically a staff member.

A Tenant Membership establishes that a global identity belongs to a tenant.

Phase 19 introduces the explicit concept:

Tenant Membership
    ↓
Tenant Staff Profile

This distinction is intentional.

Do NOT create a second authentication identity.
Do NOT duplicate password/authentication data.
Do NOT create another user table.
Do NOT make Staff a replacement for TenantMembership.

==================================================
3. PHASE 19 GOAL
==================================================

Create the foundation for a tenant staff member.

A staff record represents a person's operational employment/staff relationship with a tenant.

It must be:

- Tenant scoped
- Linked to an existing Platform User
- Linked to an existing Tenant Membership
- Explicitly lifecycle-managed
- Authorization-aware
- Audited
- Safe against cross-tenant access
- Independent from platform roles
- Independent from tenant roles/permissions
- Independent from subscription entitlement
- Independent from healthcare clinical data

The staff record is an organizational identity/profile layer.

==================================================
5. STAFF STATUS LIFECYCLE
==================================================

Define an explicit StaffStatus lifecycle.

Minimum states:

ACTIVE
SUSPENDED
DEACTIVATED

Rules:

ACTIVE → SUSPENDED
ACTIVE → DEACTIVATED

SUSPENDED → ACTIVE
SUSPENDED → DEACTIVATED

DEACTIVATED is terminal in this phase.

Do NOT implement deletion.

Do NOT silently reactivate a DEACTIVATED staff record.

Repeated transition to the current state should follow the project's established idempotency conventions.

All invalid transitions must fail safely.

==================================================
6. MEMBERSHIP RELATIONSHIP
==================================================

A Staff record can only exist for an existing TenantMembership.

The membership must belong to:

- the same tenant
- the same platform user

Staff creation must reject:

- missing membership
- membership belonging to another tenant
- membership belonging to another user
- REMOVED membership
- invalid tenant context

The exact rules for INVITED/SUSPENDED membership should be consistent with the existing TenantMembership lifecycle and authorization foundation.

Do not invent contradictory membership behavior.

A staff record must never become a bypass around TenantMembership.

==================================================
7. STAFF UNIQUENESS
==================================================

A platform user must not have multiple active staff records for the same tenant.

Prefer a schema-level uniqueness constraint that prevents duplicate tenant/user staff identity.

Do not rely only on controller checks.

If a historical DEACTIVATED staff record exists, follow the simplest safe rule consistent with the architecture.

Do not introduce staff-history/versioning complexity in this phase unless the existing schema requires it.

==================================================
8. AUTHORIZATION
==================================================

Use the existing tenant authorization system.

Do NOT create:
- global auth guards
- duplicate tenant guards
- staff-specific authentication
- client-controlled permission checks

All staff endpoints must use the established:

TrustedTenantContext
+
TenantAuthorizationGuard
+
server-defined permission metadata

Introduce a minimal staff permission namespace if the existing tenant permission system does not already contain suitable permissions.

Suggested permissions:

staff.read
staff.manage

Do not add unnecessary granular permissions yet.

Expected semantics:

staff.read
- list/read tenant staff

staff.manage
- create staff
- activate
- suspend
- deactivate
- update allowed staff administrative fields

Use the existing permission naming and storage conventions exactly.

Backfill default tenant roles consistently with previous tenant/facility/branch permissions.

Do not modify platform permissions.

==================================================
10. CREATE STAFF
==================================================

Creating staff should require an existing Platform User / Tenant Membership relationship.

Do NOT create a new Platform User automatically in this phase.

The endpoint should receive only the minimum data necessary to associate an existing tenant member with staff.

Validate all IDs and input shapes.

Creation must verify:

1. authenticated platform user
2. valid TrustedTenantContext
3. active tenant
4. valid tenant membership
5. membership belongs to current tenant
6. membership belongs to selected platform user
7. membership is eligible for staff association
8. no duplicate staff relationship exists

Do not allow the caller to select:
- tenantId as authority
- tenant roles
- platform roles
- permissions
- subscription
- entitlement
- facility ownership
- branch ownership

Those remain separate systems.

==================================================
11. FACILITY / BRANCH SCOPE
==================================================

Do NOT permanently attach Staff to a Facility or Branch in Phase 19 unless the existing architecture already requires it.

The hierarchy remains:

Tenant
  └── Facilities
        └── Branches

Staff belongs to the Tenant at this stage.

Facility/Branch assignment is a later organizational-scope capability.

Do not invent staffFacilityId or staffBranchId just because those concepts will exist later.

==================================================
12. ROLE SEPARATION
==================================================

A Staff record is NOT a role.

Do not store:
- role name
- permission list
- platform role
- tenant role

inside Staff unless the existing schema specifically requires a non-authoritative display field.

Tenant authorization remains:

TenantMembership
+
TenantRole
+
TenantPermission

Staff is only the staff identity/profile layer.

A staff member can therefore later have:
- staff profile
- one or more tenant roles
- facility/branch scope
- healthcare specialization/profile

without coupling those systems together.

==================================================
16. SECURITY
==================================================

Must test:

- unauthenticated access → 401
- missing tenant authorization → denied
- wrong tenant staff ID → not accessible
- client-supplied tenantId cannot escape tenant scope
- client-supplied membershipId cannot cross tenants
- client-supplied userId cannot associate another tenant's identity
- cross-tenant staff lookup fails
- cross-tenant mutation fails
- insufficient tenant permission fails
- deactivated staff cannot be incorrectly reactivated
- removed membership cannot create staff
- duplicate staff association rejected

Do not leak whether another tenant owns a staff record.

Use safe error behavior consistent with existing tenant resources.
