PHASE 14F — BRANCH FOUNDATION

==================================================
PRIMARY OBJECTIVE
==================================================

Introduce the Branch layer beneath Facility.

The architectural hierarchy is now:

Platform
  ↓
Tenant / Organization
  ↓
Facility
  ↓
Branch
  ↓
Future Staff / Doctors / Healthcare Operations

Important:

Tenant ≠ Facility ≠ Branch.

A Tenant may have multiple Facilities.

A Facility may have multiple Branches.

A Branch belongs to exactly one Facility.

Because Facility already belongs to exactly one Tenant, Branch therefore belongs indirectly to exactly one Tenant.

Do NOT flatten these relationships.

==================================================
1. DOMAIN MODEL
==================================================

Create a Branch model in the CENTRAL PLATFORM DATABASE.

Branch is SaaS/platform metadata.

Do NOT put Branch into MongoDB.

Relationship:

Tenant
  1
  |
  | has many
  ↓
Facility
  1
  |
  | has many
  ↓
Branch

Every Branch must belong to exactly one Facility.

Do not store a redundant tenant relationship unless there is a demonstrated architectural requirement.

Prefer deriving the tenant through:

Branch → Facility → Tenant

This avoids contradictory ownership data such as:

Branch.facilityId = Facility A
Branch.tenantId = Tenant B

If the existing architecture has a strong reason for storing tenantId directly, stop and explain the tradeoff before implementing it.

Do not silently introduce duplicated ownership fields.

==================================================
2. BRANCH FIELDS
==================================================

Use only fields required for a clean commercial foundation.

At minimum evaluate:

- id
- facilityId
- name
- code or slug if appropriate
- status
- createdAt
- updatedAt

Do not over-model the Branch.

Do NOT add:

- staff
- doctors
- departments
- specialties
- schedules
- appointment configuration
- billing configuration
- insurance configuration
- clinical configuration

Those belong to later phases.

If code/slug is implemented, uniqueness should be scoped appropriately.

Do not make Branch code globally unique without a clear architectural reason.

==================================================
3. BRANCH STATUS
==================================================

Introduce an explicit Branch lifecycle.

Recommended states:

ACTIVE
SUSPENDED
DEACTIVATED

If the existing Facility lifecycle naming and semantics already establish the canonical convention, reuse it.

Do not create a second lifecycle philosophy.

Recommended transitions:

ACTIVE → SUSPENDED
ACTIVE → DEACTIVATED

SUSPENDED → ACTIVE
SUSPENDED → DEACTIVATED

DEACTIVATED should be terminal if that is the established Facility convention.

Same-state transitions must behave consistently with Facility.

Do not physically delete Branch records.

==================================================
4. FACILITY RELATIONSHIP
==================================================

Branch must always belong to one Facility.

The Facility must exist before Branch creation.

Do not allow a Branch to reference:

- a nonexistent Facility
- a Facility belonging to another Tenant

This must be enforced at the service/repository authorization level and by database referential integrity where appropriate.

==================================================
5. TRUSTED TENANT CONTEXT
==================================================

Reuse the Phase 14D TrustedTenantContext.

Do not create another tenant context abstraction.

Branch authorization begins with:

Authenticated Platform User
+
Trusted Tenant Context
+
Tenant Authorization
+
Facility ownership/scope
+
Branch operation

The tenant context establishes the authenticated user's tenant boundary.

The Branch's Facility must resolve inside that tenant boundary.

==================================================
6. FACILITY-SCOPED SECURITY
==================================================

This is the most important addition compared with Facility.

A Branch request must verify:

Trusted Tenant
  ↓
Facility belongs to Trusted Tenant
  ↓
Branch belongs to that Facility
  ↓
Required tenant permission
  ↓
Operation allowed

Never perform:

find Branch by branchId
then trust the result.

Never perform:

find Facility by facilityId
without tenant scope.

Never trust a client-provided combination of:

tenantId
facilityId
branchId

as proof of authorization.

All identifiers supplied by the client are untrusted inputs until server-side relationships are verified.

==================================================
7. CROSS-TENANT AND CROSS-FACILITY ISOLATION
==================================================

Mandatory scenarios:

Tenant A
  Facility A1
    Branch A1-B1

Tenant A
  Facility A2
    Branch A2-B1

Tenant B
  Facility B1
    Branch B1-B1

A user authorized inside Tenant A must never access Tenant B.

A Branch under Facility A1 must never be accessible through Facility A2.

A Branch under Tenant B must never be accessible through Tenant A.

Even if the attacker knows valid:

facilityId
branchId
tenantId

the server must still verify the complete relationship.

==================================================
8. FACILITY STATUS EFFECT
==================================================

A Branch cannot operate normally under an unavailable Facility.

Determine and document the correct behavior based on the existing Facility lifecycle.

At minimum:

If Facility is DEACTIVATED:
→ Branch normal operations must be blocked.

If Facility is SUSPENDED:
→ Branch normal operations should be blocked unless the existing architecture explicitly defines otherwise.

Do not invent a new subscription/entitlement rule.

This is purely lifecycle/structural enforcement.

A Branch must not bypass its parent's Facility status.

==================================================
9. TENANT STATUS EFFECT
==================================================

Existing Tenant lifecycle rules continue to apply.

If the Tenant is not in an operational state:

Branch operations must not proceed.

Do not duplicate tenant status fields on Branch.

Resolve Tenant through the trusted tenant context / Facility relationship.

==================================================
10. AUTHORIZATION
==================================================

Reuse the existing TenantAuthorizationGuard.

Do not create a separate authorization architecture.

Define Branch permissions only if required by the existing permission model.

Inspect Phase 14E's Facility permission naming and follow the established convention.

Recommended conceptual permissions:

branches.create
branches.update
branches.suspend
branches.activate
branches.deactivate

Do not blindly duplicate these if equivalent permissions already exist.

Do not create platform permissions for Branch operations.

Branch authorization is tenant authorization.

==================================================
11. FACILITY MANAGERS / FUTURE SCOPE
==================================================

Do NOT implement facility-specific RBAC yet.

Do not create:

FacilityRole
FacilityPermission
BranchRole
BranchPermission

Tenant roles/permissions remain the current authorization model.

Future facility/branch scope restrictions may be added later as part of a dedicated authorization scope phase.

For now, tenant authorization plus structural Facility/Branch ownership is the required boundary.

Do not prematurely implement fine-grained staff scope.

==================================================
12. CREATE BRANCH
==================================================

Creation must:

1. Authenticate the user.
2. Resolve TrustedTenantContext.
3. Verify required tenant permission.
4. Resolve the Facility within the trusted tenant.
5. Confirm Facility status permits creation.
6. Validate input.
7. Create Branch under that Facility.

The client must not control ownership by arbitrary IDs.

A request such as:

{
  tenantId: "tenant-b",
  facilityId: "facility-b",
  name: "Branch"
}

must not allow a Tenant A user to create a Branch in Tenant B.

Use trusted server-side relationships.

==================================================
13. READ BRANCHES
==================================================

List branches under a Facility.

Conceptually:

GET /api/v1/tenants/:tenantId/facilities/:facilityId/branches

The tenantId is only an input to trusted tenant resolution.

The repository query must verify:

facilityId belongs to trusted tenant.

Then list Branch records belonging to that Facility.

Never list branches using facilityId alone.

For a single branch:

GET /api/v1/tenants/:tenantId/facilities/:facilityId/branches/:branchId

The query must verify the entire relationship:

Tenant
→ Facility
→ Branch

in the server-side database query.

==================================================
14. UPDATE BRANCH
==================================================

Allowed fields should be limited to Branch-owned mutable fields.

Do not allow:

facilityId changes.

A Branch must not be moved between Facilities through a generic PATCH.

Do not allow tenant changes.

If a future business requirement needs branch relocation, that should be a separate explicit operation with dedicated audit and authorization.

Do not implement relocation now.
