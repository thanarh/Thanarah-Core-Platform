PHASE 22 — DEPARTMENT & SPECIALTY FOUNDATION

You are continuing the Thanarah production SaaS architecture.

This is a REAL commercial multi-tenant healthcare SaaS system.
Do NOT treat this as a prototype.

Implement ONLY Phase 22.
Do not start Phase 23.

==================================================
1. PHASE GOAL
==================================================

Create the foundational healthcare organizational catalog for:

- Departments
- Specialties

This phase establishes the healthcare classification layer that future Doctors, Services, Appointments, and other healthcare modules can reference.

IMPORTANT:

Do NOT create:
- Doctor
- Patient
- Appointment
- Schedule
- Availability
- Medical Record
- Prescription
- Visit
- Billing
- Insurance
- MongoDB healthcare collections

This phase is ONLY the Department + Specialty foundation.

==================================================
2. ARCHITECTURAL POSITION
==================================================

Current hierarchy:

Tenant
 ├── Facility
 │     └── Branch
 │
 ├── Staff
 │     ├── Staff Roles
 │     └── Facility/Branch Scope
 │
 └── Healthcare Catalog
       ├── Departments
       └── Specialties

Important distinctions:

Staff != Doctor

Department != Role

Specialty != Permission

Facility/Branch Scope != Department

Do not merge these concepts.

A future doctor may reference:
- Staff
- Department
- Specialty
- Facility
- Branch

But that relationship is NOT implemented in Phase 22.

==================================================

Department and Specialty definitions in this phase belong to the CENTRAL Prisma database because they are tenant organizational metadata.

Do NOT create MongoDB healthcare collections.

Do NOT put patient or clinical data in Prisma.

Do NOT introduce a tenant MongoDB resolver in this phase.

==================================================
7. TENANT OWNERSHIP
==================================================

Both Department and Specialty are tenant-owned.

Every record must belong to exactly one Tenant.

Cross-tenant relationships/access must be impossible or rejected.

Never trust:

- body.tenantId
- query.tenantId
- custom headers
- client-selected permissions

TrustedTenantContext is authoritative.

If routes contain tenantId because that is the established API convention, validate it against TrustedTenantContext.

==================================================
8. DEPARTMENT STATUS
==================================================

Use an explicit lifecycle consistent with existing organizational resources.

Preferred:

ACTIVE
SUSPENDED
DEACTIVATED

If the project already has a standardized catalog lifecycle, reuse it.

Rules:

ACTIVE → SUSPENDED
ACTIVE → DEACTIVATED

SUSPENDED → ACTIVE
SUSPENDED → DEACTIVATED

DEACTIVATED is terminal.

Do not delete departments.

Do not silently reactivate DEACTIVATED departments.

Follow existing idempotency conventions for same-state transitions.

==================================================
9. SPECIALTY STATUS
==================================================

ACTIVE → DEACTIVATED

SUSPENDED → ACTIVE
SUSPENDED → DEACTIVATED

DEACTIVATED is terminal.

Do not silently reactivate DEACTIVATED specialties.

==================================================
10. NAMING / UNIQUENESS
==================================================

Determine the existing project's conventions for tenant-scoped names and codes.

At minimum:

Department names should not have accidental duplicate active definitions within the same tenant.

Specialty names should not have accidental duplicate active definitions within the same tenant.

If codes are implemented, codes must be tenant-scoped and unique.

Do NOT use global uniqueness across all tenants.

Case/whitespace normalization must follow existing validation conventions.

Do not build a complex synonym/alias system.

==================================================
11. DEPARTMENT ↔ SPECIALTY RELATIONSHIP
==================================================

IMPORTANT:

Do NOT permanently couple Department and Specialty in Phase 22 unless the existing architecture already requires that relationship.

A specialty may conceptually be used across multiple departments in a real healthcare organization.

A department may contain multiple specialties.

Therefore, do NOT implement:

departmentId directly on Specialty

unless inspection proves the existing product architecture explicitly requires one-to-one ownership.

Prefer independent tenant-scoped catalogs at this stage.

If a many-to-many relationship is truly required by an existing specification or existing implementation, implement the smallest explicit relational assignment model.

Do NOT use arrays or JSON for relationships.

If no concrete requirement exists, keep them independent in Phase 22.

Document the decision in the final report.

==================================================
12. FACILITY / BRANCH RELATIONSHIP
==================================================

Do NOT create:
