==================================================
PHASE OBJECTIVE
==================================================

Build a safe Patient Directory for tenant staff.

The directory must allow authorized tenant users to:

- list patients
- paginate patients
- filter patients
- search patients
- retrieve a patient by ID
- retrieve a patient by tenant-scoped patientNumber

This is a DIRECTORY/READ phase.

Do not expand Patient's domain model.

==================================================
1. EXISTING API CONTRACT
==================================================

Preserve the existing:

GET
/api/v1/tenants/:tenantId/patients

GET
/api/v1/tenants/:tenantId/patients/:patientId

Do not break existing response contracts unnecessarily.

Reuse the pagination contract established in Phase 26.

The collection contract currently uses:

items
limit
offset
total
hasNext

Do not introduce a second pagination system.

==================================================
2. SEARCH
==================================================

Add safe Patient directory search.

Query parameter:

search

Search should support the patient's useful directory identity fields:

- patientNumber
- firstName
- middleName
- lastName
- preferredName
- phone
- email

Do NOT search:

- nationalId by default
- address
- dateOfBirth
- clinical data
- future medical records

National ID is sensitive and must not become a casual directory search field.

Search behavior:

- case-insensitive where supported
- partial matching
- bounded input length
- whitespace normalized
- no raw Mongo query operators
- no raw regular expressions supplied directly by the client
- no arbitrary field selection
- no arbitrary Mongo filter object

The client must never be able to submit Mongo operators such as:

$regex
$where
$or
$expr
$ne
$gt
$exists

or equivalent raw query structures.

Build the Mongo query server-side from validated input.

==================================================
3. SEARCH SEMANTICS
==================================================

Do not implement a sophisticated search engine.

Use a predictable directory search.

A single search value may match any of the approved fields.

Example:

search=Ahmed

may match:

Ahmed
Ahmed Ali
Mohamed Ahmed
Ahmed123

according to the safe matching convention selected.

Document the exact behavior.

Do not introduce:
- Elasticsearch
- OpenSearch
- Atlas Search
- external search APIs
- vector search
- AI search

==================================================

status

Do not add:

5. PAGINATION
==================================================

Requirements:

- no unbounded queries
- total count must use the same filters as the result query
- hasNext must be correct

Do not change ordering without documenting the reason.

==================================================
7. DIRECTORY RESPONSE
==================================================

The directory should return only appropriate patient directory fields.

Do NOT expose:

- internal Mongo identifiers unless already part of the public ID contract
- tenant storage identifiers
- Mongo database names
- Mongo connection details
- authorization metadata
- audit metadata
- infrastructure metadata

Sensitive fields must be handled carefully.

Do not automatically expose:

- nationalId
- full address

in the list response.

The list response should be lightweight.

If the existing GET-by-ID response already exposes fields established by Phase 27, preserve that contract unless there is a demonstrated security issue.

9. PATIENT NUMBER LOOKUP
==================================================

Support safe tenant-scoped retrieval by patientNumber if the existing API architecture permits it.

If the existing routing conventions make this inappropriate, use the project's established alternative.

- no global lookup
- no cross-tenant leakage

Do not make patientNumber globally unique.

Do not change tenant authorization architecture.

11. STORAGE BOUNDARY
==================================================

This phase MUST NOT bypass Phase 29/30 architecture.

Patient reads must continue through:

TrustedTenantContext
→ Tenant Storage Resolver
→ Patient Repository
→ Persistent Tenant Storage
→ MongoDB

Do NOT import PrismaClient into Patient code.

Do NOT query central MySQL for Patient directory data.

Do NOT query Mongo directly from controllers.

==================================================
12. MONGO QUERY SAFETY
==================================================

All search/filter values must be validated before reaching the repository.

The repository must build queries structurally.

Do NOT accept:

Record<string, unknown>

as a raw query parameter from the controller.

Do NOT pass request.query directly into Mongo.

Do NOT allow arbitrary projection.

Do NOT allow arbitrary sorting.

Sorting must remain server-defined.

==================================================
13. PERFORMANCE
==================================================

This is a directory feature.

Avoid obviously expensive queries.

Do not:

- load every patient into memory
- perform application-side filtering over the entire collection
- perform application-side pagination after fetching all records
- perform N+1 queries
- create one Mongo connection per request

Filtering, sorting, and pagination should happen in Mongo.

Count and list queries must use equivalent filters.

Do not introduce caching in this phase.

- searchable identity fields

Do NOT create an index for every searchable field automatically.

Do not add speculative indexes.

If a search index is not appropriate for the current Mongo implementation, use the safest reasonable query strategy and document the limitation.

Do not introduce Mongo Atlas Search.

15. PRIVACY
==================================================

- bounded result size
- tenant isolation

Do not expose sensitive patient fields in collection results unnecessarily.

Do not log search terms together with full patient data.

Do not log patient records.
