==================================================
PHASE OBJECTIVE
==================================================

Improve Patient data quality by introducing a safe duplicate-detection mechanism during Patient creation and, where justified, update.

The purpose is NOT to automatically merge patients.

The purpose is to detect likely duplicate records and prevent accidental creation when there is strong evidence that the same person may already exist.

IMPORTANT:

Do NOT make duplicate detection a medical identity engine.

Do NOT use AI.

Do NOT use fuzzy matching libraries.

Do NOT introduce external search infrastructure.

Do NOT make probabilistic guesses.

Use deterministic, explainable matching rules only.

==================================================
1. FIRST INSPECT EXISTING PATIENT MODEL
==================================================

Inspect:

- Patient model/domain
- Patient DTOs
- Patient repository
- Patient service
- Patient controller
- Patient storage adapter
- Mongo indexes
- Patient validation
- Patient directory search
- audit implementation
- existing error conventions
- existing API response conventions

Do not duplicate existing normalization utilities.

Reuse established project conventions.

==================================================
2. NORMALIZATION
==================================================

Create or reuse deterministic normalization for duplicate comparison.

Only normalize values for comparison.

Do NOT modify the stored patient data unless the existing domain contract explicitly requires normalization.

Potential comparison fields:

- phone
- email
- firstName
- middleName
- lastName
- dateOfBirth

Do NOT use:
- nationalId as a default duplicate detector
- address
- clinical information
- medical history

Do not assume national ID is safe or universally available.

==================================================
3. DUPLICATE DETECTION RULE
==================================================

Implement deterministic duplicate detection.

Do NOT create a vague "similarity score".

Do NOT use fuzzy matching.

Use explicit matching rules.

A patient should be considered a likely duplicate only when a strong combination of identity fields matches.

Example deterministic combinations may include:

A.
normalized phone + normalized name

OR

B.
normalized email + normalized name

OR

C.
normalized firstName + normalized lastName + dateOfBirth

The exact combinations must be chosen based on the existing Patient fields and validation conventions.

Document the exact rule.

Do NOT use a single weak field such as:

firstName alone
lastName alone
phone alone
email alone

as sufficient proof of duplication.

==================================================
4. TENANT SCOPE
==================================================

Duplicate detection is strictly TENANT-SCOPED.

Tenant A:
John Doe
phone X

Tenant B:
John Doe
phone X

must NOT be considered a duplicate across tenants.

Never perform global Patient searches.

All duplicate detection queries must operate through:

TrustedTenantContext
→ Tenant Storage
→ Patient Repository

==================================================
5. CREATE BEHAVIOR
==================================================

Before creating a Patient:

1. Validate payload.
2. Normalize comparison fields.
3. Perform deterministic duplicate check.
4. If no likely duplicate:
   create normally.
5. If likely duplicate:
   return a safe duplicate response.

Do NOT automatically create the patient anyway.

Do NOT silently merge.

Do NOT modify the existing Patient.

Do NOT delete anything.

==================================================
6. DUPLICATE ERROR CONTRACT
==================================================

Create a dedicated domain/application error if one does not already exist.

Conceptually:

PATIENT_DUPLICATE_POSSIBLE

The HTTP response must be safe.

It may include enough information for the authorized staff user to understand that a possible duplicate exists.

Do NOT expose:
- internal Mongo IDs
- storage metadata
- another tenant's information
- sensitive patient data unnecessarily

If an existing Patient ID must be returned to allow staff to review the record, ensure it is:
- within the same tenant
- authorized
- intentionally exposed by the API contract

Do not expose a global search result.

==================================================
7. DUPLICATE REVIEW FLOW
==================================================

Do NOT implement a full duplicate-management workflow.

For this phase, the minimum behavior is:

Create Patient
      ↓
Duplicate check
      ↓
No duplicate → create
Possible duplicate → safe rejection

Do NOT add:

- merge
- unlink
- duplicate resolution dashboard
- duplicate status
- duplicate records table
- manual merge
- audit workflow for resolving duplicates

Those are separate future capabilities.

==================================================
8. UPDATE BEHAVIOR
==================================================

Duplicate detection on update must avoid comparing the patient against itself.

If a Patient updates:

phone
email
name
dateOfBirth

the duplicate detector must exclude the current Patient ID.

Example:

Patient A updates their own phone.

The duplicate check must not detect Patient A as a duplicate of itself.

If another Patient matches the deterministic rule:

return the same safe duplicate response.

Do not modify the other patient.

==================================================
9. READ-ONLY DUPLICATE CHECK
==================================================

If useful for the frontend, you MAY expose a dedicated read-only duplicate-check endpoint.

Only if it fits the existing API conventions.

Preferred conceptual shape:

POST
/api/v1/tenants/:tenantId/patients/check-duplicate

This endpoint:

- requires tenant.patients.read
- does NOT create or modify data
- returns only same-tenant possible matches
- uses the exact same duplicate detection service used by create/update
- does not expose sensitive information unnecessarily

Do NOT create this endpoint if the architecture already has a suitable validation/preflight convention.

Do not duplicate duplicate-detection logic between controller and service.

- selectivity
- tenant scope
- storage size implications

If new indexes are needed, add only those required by the implemented deterministic rules.

Do not introduce speculative indexes.

20. CONCURRENCY
==================================================

This is important.

Two simultaneous requests may attempt to create the same Patient.

Application-level duplicate detection alone is NOT sufficient to guarantee uniqueness.

Do not claim strong uniqueness unless backed by database constraints.

For this phase:

- deterministic duplicate detection is the user-facing safety mechanism
- existing patientNumber uniqueness remains database-enforced
- do not invent a global identity uniqueness constraint

If the chosen duplicate rules require a database uniqueness guarantee, explain the limitation instead of creating an unsafe constraint.

Do not create a uniqueness constraint that could incorrectly prevent legitimate patients.
