Use:

==================================================
2. PLAN VS SUBSCRIPTION
==================================================

This distinction is mandatory.

Plan:

A reusable platform-defined commercial package.

Subscription:

A Tenant-specific assignment to a Plan for a defined period/lifecycle.

Example:

Plan:
PRO

Tenant:
Tenant A

Subscription:
Tenant A → PRO
starts: 2026-10-01
ends: 2026-11-01

Do not put tenantId on Plan.

Do not put subscriptionId on Plan.

Plan remains reusable.

==================================================
3. SUBSCRIPTION MODEL
==================================================

Create a Subscription model using existing Prisma conventions.

At minimum evaluate:

- id
- tenantId
- planId
- status
- startsAt
- endsAt
- cancelledAt
- createdAt
- updatedAt

Only add additional fields if they are necessary for a clean lifecycle.

Do NOT add:

- price
- currency
- billingInterval
- paymentProvider
- externalSubscriptionId
- invoiceId
- paymentMethodId
- autoCharge
- gateway metadata

Those belong to future billing/payment phases.

==================================================
4. SUBSCRIPTION STATUS
==================================================

Use an explicit lifecycle.

Recommended states:

TRIALING
ACTIVE
PAST_DUE
SUSPENDED
CANCELLED
EXPIRED

However, BEFORE implementing:

Inspect the existing architecture and determine whether every one of these states is justified in this phase.

Important:

PAST_DUE is normally billing-related.

Since billing is explicitly OUT OF SCOPE, do NOT introduce PAST_DUE merely because it is common in subscription systems.

Prefer the smallest correct lifecycle for this phase.

A reasonable initial lifecycle may be:

TRIALING
ACTIVE
SUSPENDED
CANCELLED
EXPIRED

If you choose a different lifecycle, document why.

Do not create speculative statuses.

==================================================
5. STATUS SEMANTICS
==================================================

Define clear meanings.

TRIALING:

Tenant has a temporary subscription period before normal active service.

ACTIVE:

Subscription is currently active.

SUSPENDED:

Subscription has been explicitly suspended by an authorized platform operation.

CANCELLED:

Subscription has been cancelled.

EXPIRED:

Subscription period ended without remaining active entitlement.

Important:

Do not confuse:

CANCELLED

with:

EXPIRED.

Cancellation is an explicit lifecycle action.

Expiration is a period-based state.

Do not automatically run expiration jobs in this phase.

==================================================
6. DATE SEMANTICS
==================================================

Use explicit UTC timestamps.

startsAt:
When the subscription period begins.

endsAt:
When the current subscription period ends.

cancelledAt:
When cancellation occurred.

Rules:

- startsAt is required.
- endsAt may be nullable only if the architecture explicitly supports open-ended subscriptions.
- cancelledAt is nullable.
- cancelledAt should only exist after cancellation.
- cancelledAt must not be earlier than startsAt.
- endsAt must not be earlier than startsAt.

Do not use local server time.

Use DateTime/UTC consistently with the existing project.

==================================================
7. CURRENT SUBSCRIPTION
==================================================

This is critical.

A Tenant may have historical subscriptions.

Example:

Tenant A:

Subscription 1
FREE
EXPIRED

Subscription 2
PRO
CANCELLED

Subscription 3
ENTERPRISE
ACTIVE

Only Subscription 3 is current.

The system must prevent contradictory current subscriptions.

Define a clear invariant for the current effective subscription.

Do NOT simply assume:

"latest created subscription = current subscription."

Current state must be determined from explicit lifecycle/date semantics.

==================================================
8. CONCURRENT SUBSCRIPTIONS
==================================================

Do not allow two simultaneously effective subscriptions for the same Tenant if the architecture defines only one current subscription.

The database and/or service layer must protect this invariant as far as practical.

Think about race conditions:

Request A:
creates ACTIVE subscription for Tenant X

Request B:
simultaneously creates ACTIVE subscription for Tenant X

Both must not succeed if that would violate the single-current-subscription invariant.

Do not rely only on application-level "check then insert".

Use an appropriate database strategy compatible with MySQL/MariaDB and the existing Prisma architecture.

If MySQL does not support the exact partial unique index semantics needed, use a safe transactional/service strategy and document it.

Do not invent unsupported Prisma schema syntax.

==================================================
9. HISTORICAL SUBSCRIPTIONS
==================================================

Do NOT delete old subscriptions.

Subscription history is commercially important.

A Tenant should be able to have:

historical
+
current

subscriptions.

Do not mutate old subscriptions into unrelated plans just to represent an upgrade.

Future upgrades/downgrades should create new subscription periods/records according to a future commercial workflow.

That workflow is NOT implemented now.

==================================================
10. PLAN LIFECYCLE INTERACTION
==================================================

A Subscription references a Plan.

Important case:

A Plan becomes INACTIVE or ARCHIVED after an existing Tenant subscription references it.

Do NOT automatically delete or rewrite the Subscription.

Historical subscription integrity must remain.

Do not automatically migrate the Tenant to another Plan.

Do not automatically cancel the Subscription merely because the Plan is archived.

For NEW subscriptions:

an inactive/archived Plan must not be assignable.

For existing subscriptions:

preserve historical relationship.

Document this explicitly.

==================================================
11. TENANT LIFECYCLE INTERACTION
==================================================

Subscription belongs to a Tenant.

Do not create a subscription for a nonexistent Tenant.

Do not allow a removed/deactivated Tenant to receive a new subscription.

However, historical subscription records must remain available for audit/history.

Do not cascade-delete subscription history when Tenant status changes.

Use the existing Tenant lifecycle semantics.

Do not invent a second Tenant lifecycle.

==================================================
15. CREATE SUBSCRIPTION
==================================================

Creation must:

1. Authenticate platform administrator.
2. Verify platform permission.
3. Resolve Tenant.
4. Verify Tenant exists.
5. Verify Tenant can receive a subscription.
6. Resolve Plan.
7. Verify Plan exists.
8. Verify Plan is ACTIVE.
9. Validate dates.
10. Verify no conflicting current subscription exists.
11. Create subscription atomically.
12. Audit the operation.

Do not allow the client to bypass these rules.

Do not accept an arbitrary status from the client.

For example, do NOT allow:

{
  status: "ACTIVE"
}

to blindly determine lifecycle.

The service decides initial status according to the supported business operation.

==================================================
16. PLAN ASSIGNMENT
==================================================

Subscription creation must reference an existing Plan.

Do not create a new Plan automatically.

Do not accept:

planName

as a replacement for planId unless the API contract explicitly defines a lookup mechanism.

Prefer stable plan ID/key resolution on the server.

Verify the Plan is active.

==================================================
17. TENANT ASSIGNMENT
==================================================

Subscription tenant ownership must come from the authorized platform operation.

Do not create a Subscription for a tenant based solely on a client-controlled hidden field.

Because this is a platform administrative API, the requested tenantId is an input, but the service must validate it against the central Tenant record and its lifecycle.

Do not trust arbitrary tenant IDs as authorization.

The authenticated platform administrator's platform permissions control the operation.

==================================================
18. CANCEL
==================================================

Cancellation must be explicit.

Cancellation should:

- set appropriate status
- set cancelledAt
- preserve historical record
- not delete Subscription
- not delete Plan
- not delete Tenant data

Do not implement automatic payment cancellation because payments do not exist yet.

If the existing business semantics support "cancel at period end", do NOT implement that unless necessary.

Keep cancellation simple and explicit.

==================================================
19. SUSPEND / ACTIVATE
==================================================

If SUSPENDED is included:

Implement explicit lifecycle transitions.

Example:

ACTIVE → SUSPENDED
SUSPENDED → ACTIVE

Validate transitions server-side.

Do not accept arbitrary status changes.

Do not let clients directly mutate status.

If TRIALING is included:

Define explicitly which transitions are valid.

For example:

TRIALING → ACTIVE
TRIALING → CANCELLED
TRIALING → EXPIRED

Do not invent transitions without documenting them.

==================================================
20. EXPIRATION
==================================================

Do NOT build a scheduler or background worker.

Do NOT implement automatic expiration jobs.

However, the service must have a clear model for expired subscriptions.

If a request encounters a subscription whose endsAt is already in the past, do not silently claim it is active.

Choose a consistent approach:

- explicit lifecycle transition service
OR
- effective-state calculation

and document it.

Do not create hidden background mutation.

Do not silently mutate database state during arbitrary reads unless the architecture already has such a pattern.

Prefer explicit lifecycle state.

==================================================
21. CURRENT SUBSCRIPTION QUERY
==================================================

Provide a safe repository/service capability to resolve the current effective subscription for a Tenant.

It must not:

- trust latest created record
- return cancelled/expired records as active
- cross tenant boundaries
- ignore subscription dates

It must use server-side lifecycle/date rules.

This capability is foundational for later entitlement enforcement.

Do NOT implement entitlement enforcement now.

31. CONCURRENCY / TRANSACTIONS
==================================================

Subscription creation and current-subscription conflict handling must be transaction-safe.

Do not implement:

then insert

as two unrelated operations without considering race conditions.

Use Prisma transactions and an appropriate isolation/locking strategy compatible with MySQL/MariaDB.

If the database constraint cannot fully represent "one current subscription" because of nullable/date semantics, enforce it safely in the service transaction and document the invariant.

Do not claim concurrency safety without testing or explaining the mechanism.
