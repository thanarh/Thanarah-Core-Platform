PHASE 18 — USAGE LIMITS & QUOTA FOUNDATION

==================================================
PRIMARY OBJECTIVE
==================================================

Introduce the foundation for plan-based usage limits.

The system must distinguish:

AUTHORIZATION
"Is this user allowed to perform this operation?"

ENTITLEMENT
"Does the Tenant's current plan include this feature?"

QUOTA
"Is the Tenant currently within the allowed usage limit?"

These are three separate concepts.

Future business operations may require:

Authentication
+
Tenant Authorization
+
Feature Entitlement
+
Quota Availability

Do NOT merge these layers.

==================================================
STRICT SCOPE
==================================================

Implement only:

- Plan-level usage limit definitions
- PlanFeature/Plan quota configuration where architecturally appropriate
- Usage limit definition/value resolution
- Quota decision service
- Tenant-scoped quota evaluation
- Clear quota result/error semantics
- Guard/decorator foundation if justified
- Tests
- Documentation
- Prisma migration ONLY if genuinely required

Do NOT implement:

- Actual usage counters
- Usage event ingestion
- Metering pipelines
- Redis
- Background workers
- Scheduled aggregation
- Billing
- Payments
- Invoices
- Subscription checkout
- Upgrade workflow
- Downgrade workflow
- Renewal workflow
- Healthcare
- Patients
- Doctors
- Staff
- Appointments
- Scheduling
- MongoDB
- Tenant database provisioning
- Facility-level RBAC
- Branch-level RBAC
- Voice AI
- Ownership handoff

STOP after Phase 18.

==================================================
1. IMPORTANT ARCHITECTURAL DECISION
==================================================

Do NOT create arbitrary quota tables just because quota systems commonly have them.

First inspect Phase 15 PlanFeature configuration.

If PlanFeature already supports a safe configuration structure, prefer extending that established architecture rather than introducing duplicate quota configuration models.

The goal is:

Plan
  ↓
PlanFeature
  ↓
Feature
  +
optional limit configuration

Example conceptual configuration:

PATIENTS
  enabled: true
  max: 1000

BRANCHES
  enabled: true
  max: 3

STAFF
  enabled: true
  max: 10

However:

Do NOT assume these exact feature keys exist.

Do NOT create healthcare feature records merely to demonstrate quotas.

Do NOT create actual usage counters.

==================================================
2. ENTITLEMENT VS QUOTA
==================================================

Mandatory separation:

Feature Entitlement:

"Is this feature included?"

Quota:

"How much of this feature/resource is allowed?"

Example:

Plan includes:
BRANCHES

Quota:
max = 3

Tenant currently has:
3 branches

Result:

ENTITLED = YES
QUOTA AVAILABLE = NO

Therefore the next creation must eventually be blocked.

But Phase 18 does NOT implement Branch creation enforcement.

It only establishes the quota decision foundation.

==================================================
3. QUOTA RESOURCE DEFINITION
==================================================

Create a stable server-defined representation for quota resources.

A quota resource is NOT necessarily the same thing as a Feature.

Examples:

BRANCHES
STAFF
PATIENTS
STORAGE_BYTES

These are conceptual examples only.

Do not add every future resource.

Inspect the existing Feature/PlanFeature architecture.

Prefer stable machine-readable keys.

Do not accept arbitrary quota keys from clients.

==================================================
4. LIMIT TYPES
==================================================

Keep the first implementation intentionally small.

At minimum support:

COUNT

If configuration needs to distinguish unlimited:

UNLIMITED

or an explicit null/unbounded representation.

Do not implement:

- time-series limits
- rate limits
- bandwidth limits
- storage billing
- API request billing
- token billing
- per-minute quotas

Those belong to future metering phases.

==================================================
5. LIMIT VALUE SEMANTICS
==================================================

Define clear semantics.

Examples:

max = 10

means:

currentUsage < 10
→ quota available

currentUsage >= 10
→ quota exceeded

Do not allow negative limits.

Do not allow NaN/infinite values.

Use safe integer validation.

If unlimited is supported, represent it explicitly rather than using magic values such as:

-1
-999999
999999999

unless the existing architecture already defines such a convention.

Prefer explicit semantics.

==================================================
6. NO USAGE COUNTERS YET
==================================================

This phase MUST NOT create real usage counters.

Do NOT create:

TenantUsage
UsageCounter
UsageEvent
MeteringEvent

unless the existing architecture already contains one and the implementation genuinely requires it.

We are creating:

Quota Definition
+
Quota Decision Contract

not:

Quota Metering System.

==================================================
7. QUOTA DECISION SERVICE
==================================================

Create a dedicated:

TenantQuotaService

or equivalent.

It must remain separate from:

TenantAuthorizationService
TenantEntitlementService

Conceptual API:

checkQuota(
  trustedTenantContext,
  resourceKey,
  currentUsage
)

or an equivalent strongly typed API.

The service should resolve:

Trusted Tenant
→ Current Subscription
→ Plan
→ Relevant PlanFeature/configuration
→ Limit
→ Compare with supplied usage
→ Decision

IMPORTANT:

currentUsage is only an input to the decision contract in this phase.

It is NOT persisted by Phase 18.

==================================================
8. CURRENT SUBSCRIPTION
==================================================

Reuse Phase 16 current subscription logic.

Do NOT implement another definition of current subscription.

Do NOT select:

latest subscription

as a fallback.

Only the effective current subscription may determine quota configuration.

If no active subscription:

→ quota unavailable

Fail closed.

==================================================
9. PLAN STATUS
==================================================

Respect Phase 17 behavior.

If the current subscription references:

INACTIVE
or
ARCHIVED

Plan:

quota must not be treated as available.

Do not migrate the Tenant.

Do not rewrite Subscription.

Do not automatically assign another Plan.

==================================================
10. SUBSCRIPTION STATUS
==================================================

Quota configuration is available only for an effective subscription.

At minimum:

ACTIVE → eligible

SUSPENDED → not eligible

CANCELLED → not eligible

EXPIRED → not eligible

TRIALING is not currently implemented and must not be invented.

==================================================
11. FEATURE ENTITLEMENT
==================================================

Quota evaluation must NOT bypass Feature entitlement.

If the relevant Feature is not entitled:

→ quota is NOT available

Correct sequence:

Current Subscription
→ Plan
→ PlanFeature
→ Feature
→ Feature Entitlement
→ Quota Configuration

Do not treat a quota as permission to use a feature.

==================================================
12. FEATURE WITHOUT QUOTA
==================================================

A feature may be entitled without having a finite quota.

Examples:

A feature may simply be:

enabled = true

with no maximum.

Interpret this carefully.

If the feature has no quota configured:

The quota layer should return something equivalent to:

NO_LIMIT_CONFIGURED

not:

QUOTA_EXCEEDED

and not:

DENIED

The final business policy can decide whether unlimited/no-limit is allowed.

Do not invent arbitrary defaults.

==================================================
13. UNLIMITED
==================================================

If explicit unlimited is supported:

UNLIMITED
→ quota available

even if currentUsage is high.

But still require:

- valid tenant context
- active subscription
- active plan
- active feature entitlement

Unlimited does not bypass entitlement.

==================================================
14. CURRENT USAGE INPUT
==================================================

Validate currentUsage:

- integer
- non-negative
- finite
- safe integer

Reject invalid values.

Do not trust client-supplied usage as actual production usage.

Document clearly:

Phase 18 currentUsage is a decision input for the quota contract.

Future production usage will come from a trusted usage/metering source.

==================================================
15. FUTURE USAGE SOURCE
==================================================

Document the future architecture:

Business Operation
  ↓
Trusted Usage Source
  ↓
Current Usage
  ↓
Quota Decision

Possible future usage sources:

- database counts
- usage event aggregation
- dedicated metering
- storage accounting

Do NOT implement these now.

==================================================
16. QUOTA RESULT
==================================================

Prefer a structured decision.

Conceptually:

AVAILABLE
EXCEEDED
NO_LIMIT_CONFIGURED
NOT_ENTITLED
NO_SUBSCRIPTION
INVALID_CONTEXT

Use project conventions where available.

Do not expose excessive internal details through HTTP responses.

A future business route may convert:

EXCEEDED

into a stable 403 or 409 according to business semantics.

Do not attach quota enforcement to existing business APIs in Phase 18.

==================================================
17. QUOTA ERROR
==================================================

If a quota guard is implemented, define a stable application error.

Example:

QUOTA_EXCEEDED

Do not expose:

current usage
maximum
plan name
internal feature configuration

unless explicitly intended by a future product-facing API.

Keep default errors safe.

==================================================
18. QUOTA GUARD
==================================================

Do NOT automatically create a global quota guard.

If a guard is useful for future composition, create a dedicated:

TenantQuotaGuard

but keep it:

- non-global
- route-scoped
- server-configured
- independent from TenantAuthorizationGuard
- independent from TenantEntitlementGuard

A future route may conceptually use:

@RequireTenantPermissions(...)
@RequireTenantFeature(...)
@RequireTenantQuota(...)

Do NOT attach these decorators to healthcare routes because those routes do not exist yet.

==================================================
19. QUOTA DECORATOR
==================================================

If implemented, quota metadata must be server-defined.

Conceptually:

@RequireTenantQuota("BRANCHES")

The resource key must not come from:

- request body
- query
- headers
- cookies
- arbitrary client input

Do not allow:

@RequireTenantQuota(req.body.resource)

==================================================
20. PERMISSION + ENTITLEMENT + QUOTA
==================================================

Document the future combined gate:

Authentication
        ↓
Tenant Membership
        ↓
Tenant Permission
        ↓
Feature Entitlement
        ↓
Quota Availability
        ↓
Business Operation

Each layer has a different responsibility.

Do not collapse them into one "canAccess" boolean without preserving the underlying decision reasons internally.

==================================================
21. TENANT ISOLATION
==================================================

Quota decisions are tenant-scoped.

Tenant A's:

- Subscription
- Plan
- Feature
- Limit

must never affect Tenant B.

The service must require TrustedTenantContext.

Do not accept tenantId as the source of truth.

Do not allow:

client tenantId
→ quota lookup

without trusted context.

==================================================
22. CLIENT INPUT
==================================================

Never trust client input for:

- planId
- subscriptionId
- featureId
- featureKey
- quota resource
- limit
- entitlement
- actual usage

Only currentUsage may be accepted as a contract input for Phase 18 testing/decision evaluation, and it must be treated as untrusted measurement data rather than authoritative usage.

The actual plan and limit always come from server-side records.

==================================================
23. CACHING
==================================================

Do NOT introduce external cache.

Do NOT introduce distributed cache.

If an existing safe cache abstraction exists, inspect it first.

Otherwise do not add caching.

Future cache invalidation will need to consider:

- Plan changes
- PlanFeature changes
- Subscription changes
- Feature status changes

Document this future consideration if relevant.
