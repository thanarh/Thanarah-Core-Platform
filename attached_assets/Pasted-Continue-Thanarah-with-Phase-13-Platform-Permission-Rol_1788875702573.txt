Implement ONLY the Platform Permission & Role Authorization Guard.

==================================================
1. OBJECTIVE
==================================================

Add a separate authorization layer on top of PlatformAuthGuard.

Authentication answers:
"Who is this user?"

Authorization answers:
"Is this authenticated platform user allowed to perform this action?"

Do NOT merge authorization into PlatformAuthGuard.

PlatformAuthGuard must remain responsible only for authentication.

==================================================
4. DECORATORS
==================================================

Create a clean declarative mechanism for route requirements.

Example:

@RequirePermissions('platform_users.read')

and support multiple permissions where appropriate.

The decorator must only declare requirements.

It must not contain authorization logic.

If a role-based requirement is necessary, provide a separate declarator rather than mixing it into permission metadata.

Do not add unnecessary abstractions.

==================================================
5. AUTHORIZATION GUARD
==================================================

Create a dedicated PlatformAuthorizationGuard.

Expected pipeline:

1. PlatformAuthGuard establishes authenticatedPlatformUser.
2. Authorization guard reads the required permission metadata.
3. If the route has no authorization metadata, preserve the existing behavior according to the project's chosen convention.
4. Resolve the authenticated user's platform roles.
5. Resolve the permissions granted by those roles.
6. Check the required permission(s).
7. Allow only when authorization requirements are satisfied.
8. Otherwise return a stable forbidden error.

Do NOT trust permissions supplied by:
- request body
- query
- route parameters
- headers
- client-controlled cookies
- arbitrary JWT fields beyond the trusted role identifiers already defined by the authentication architecture.

The authorization decision must be server-side.

==================================================
6. ROLE/PERMISSION RESOLUTION
==================================================

Do not place the full permission list into the JWT.

The existing JWT must remain minimal.

The guard must resolve authorization using trusted server-side role/permission data.

Do not duplicate role definitions inside the guard.

Use the existing repository/service layer where possible.

Do not access Prisma directly from the guard if an appropriate service/repository abstraction already exists.

==================================================
7. PROTECTED ROLE RULES
==================================================

Preserve the existing protected-role semantics.

OWNER and SUPER_ADMIN have the broad platform permissions already defined.

PLATFORM_ADMIN:
- platform.read
- platform_users.*
- roles.read
- roles.assign

SECURITY_ADMIN:
- sessions.*
- audit_logs.read
- security_events.*
- system_health.read

SUPPORT_ADMIN:
- platform.read
- platform_users.read
- system_health.read

Do not silently grant additional permissions.

Important:

SUPER_ADMIN/PLATFORM_ADMIN must not automatically gain the ability to assign the OWNER role merely because they have roles.assign.

OWNER assignment must remain restricted according to the existing protected-role security rules.

If the existing architecture does not yet expose this behavior through an authorization service, create only the minimal policy abstraction needed for this rule.

with
403 authorization failures.
