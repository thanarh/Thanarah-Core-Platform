==================================================
1. PLATFORM AUTHENTICATION REMAINS SEPARATE
==================================================

Do not modify PlatformAuthGuard semantics.

PlatformAuthGuard answers:

"Is this a valid authenticated platform user?"

Tenant authorization answers:

"Does this authenticated user have permission to perform this operation inside this tenant?"

Keep these separate.

Required conceptual order:

PlatformAuthGuard
→ TrustedTenantContext
→ TenantAuthorization

Do not merge tenant authorization into PlatformAuthGuard.

Do not make TenantAuthorizationGuard global.

Do not affect:

/health
/ready
/docs

or public login/refresh routes.

==================================================
2. TRUSTED TENANT CONTEXT
==================================================

Use the TrustedTenantContext contract created in Correction 6.

Do NOT create a second competing tenant-context abstraction.

Tenant context must come from trusted server-side resolution.

Never trust a client-provided tenant ID as authorization.

A route may contain a tenant identifier such as:

/api/v1/platform/tenants/:tenantId/...

but the parameter is only an input to resolution.

It is NOT automatically a trusted TenantContext.

The server must resolve and validate it.

==================================================
3. TENANT CONTEXT RESOLUTION
==================================================

Create or complete the runtime tenant-context resolver.

Given an authenticated platform user and a requested tenant identity:

1. Resolve the Tenant.
2. Confirm the Tenant exists.
3. Confirm the Tenant is in a state that permits the requested operation.
4. Confirm the authenticated user has an appropriate active membership.
5. Construct TrustedTenantContext only after those checks succeed.

Do not construct TrustedTenantContext before membership validation.

Do not use tenant ID alone.

Do not use hostname alone.

Do not use UUID secrecy.

Do not use a client-supplied role or permission.

Fail closed.

==================================================
4. MEMBERSHIP VALIDATION
==================================================

Only an appropriate active membership may satisfy tenant access.

At minimum:

- INVITED must not authorize normal tenant operations.
- SUSPENDED must not authorize normal tenant operations.
- REMOVED must not authorize normal tenant operations.
- ACTIVE may continue to tenant authorization.

Use the existing TenantMembership lifecycle.

Do not modify membership lifecycle semantics unless required to fix a demonstrated authorization bug.

The authenticated user must be the member being evaluated.

Never accept a client-provided user ID as the membership subject.

==================================================
5. TENANT ROLE/PERMISSION RESOLUTION
==================================================

Resolve effective tenant permissions from:

Authenticated Platform User
+
Trusted Tenant Context
+
Active Tenant Membership
+
Assigned Tenant Role(s)
+
Tenant Role Permissions

Do not trust:

- request body roles
- query permissions
- arbitrary headers
- cookies
- client-provided role IDs
- client-provided permission IDs
- JWT tenant permission claims
- tenant ID alone

All effective permissions must come from the central database/server-side state.

==================================================
6. TENANT AUTHORIZATION SERVICE
==================================================

Create a dedicated TenantAuthorizationService or equivalent policy service.

It should support the minimum operations required by runtime authorization.

For example:

- authorize tenant permission
- resolve effective tenant permissions
- verify membership
- verify tenant role assignment

Use explicit methods.

Do not create a generic authorization engine that mixes platform and tenant authorization.

Do not access Prisma from controllers.

Follow:

Controller
→ Guard/Policy
→ Service
→ Repository
→ Prisma

==================================================
7. TENANT AUTHORIZATION GUARD
==================================================

Create a dedicated TenantAuthorizationGuard.

It must:

1. Ensure the request is authenticated.
2. Resolve trusted tenant context.
3. Validate active membership.
4. Resolve tenant roles/permissions.
5. Read server-defined required tenant permissions.
6. Enforce authorization.
7. Fail closed.

Do not allow required permissions to come from request input.

Do not use PlatformAuthorizationGuard to evaluate tenant permissions.

Do not silently fall back to platform permissions.

==================================================
8. PERMISSION DECORATOR
==================================================

Create or complete a clear tenant-specific permission metadata mechanism.

If platform authorization uses:

@RequirePermissions(...)

do not create ambiguity between platform and tenant permissions.

Use an explicit tenant-specific decorator/metadata mechanism if needed.

Conceptually:

@RequireTenantPermissions(...)

and:

@RequirePlatformPermissions(...)

must remain distinguishable.

Use the project's existing naming conventions if they provide a better equivalent.

==================================================
9. 401 VS 403
==================================================

Preserve correct HTTP semantics.

Unauthenticated:
→ 401

Authenticated but:

- no tenant membership
- inactive membership
- missing tenant permission
- tenant role insufficient

→ 403

Do not expose sensitive information about whether another tenant exists.

Avoid turning tenant lookup into an information-disclosure oracle.

Use stable safe application errors.

==================================================
10. CROSS-TENANT ISOLATION
==================================================

This is a mandatory security requirement.

Test scenarios such as:

User A:
Tenant A membership
Tenant A role

Request:
Tenant B

must fail.

A role belonging to Tenant A must never authorize operations in Tenant B.

A membership belonging to Tenant A must never satisfy membership checks for Tenant B.

A tenant permission from Tenant A must never authorize Tenant B.

A valid authenticated platform user must not automatically gain access to every tenant.

Tenant A context must never be interchangeable with Tenant B context.

Use explicit tenant ownership checks throughout the resolution path.

==================================================
11. TENANT STATUS
==================================================

Tenant lifecycle status must participate in runtime authorization appropriately.

At minimum determine safe behavior for:

ACTIVE
SUSPENDED
DEACTIVATED

Do not allow normal tenant operations against a tenant state that should block access.

Use the actual Phase 14A status model rather than inventing a second status system.

Do not implement subscription entitlement yet.

Tenant status and subscription status are separate concepts.

==================================================
12. OWNER / ADMIN BEHAVIOR
==================================================

Use the Tenant OWNER/ADMIN roles implemented in Phase 14C.

Do not introduce new ownership semantics.

Ensure:

- OWNER permissions are tenant-scoped.
- ADMIN permissions are tenant-scoped.
- Platform OWNER is unrelated to Tenant OWNER.
- Tenant OWNER cannot grant platform permissions.
- Tenant ADMIN cannot grant platform permissions.

Do not implement ownership transfer in this phase.

The previously proposed ownership-handoff follow-up is explicitly out of scope.

==================================================
14. PLATFORM VS TENANT AUTHORIZATION
==================================================

This distinction must remain absolute.

Platform:

PlatformUser
→ PlatformRole
→ PlatformPermission

Tenant:

PlatformUser
→ TenantMembership
→ TenantRole
→ TenantPermission

A platform permission must not automatically satisfy a tenant permission.

A tenant permission must never satisfy a platform permission.

A platform administrator managing SaaS metadata uses platform authorization.

A tenant member operating tenant business functionality uses tenant authorization.

- passwords

- secrets
- credentials
- DATABASE_URL

Avoid logging excessive tenant-sensitive information.
