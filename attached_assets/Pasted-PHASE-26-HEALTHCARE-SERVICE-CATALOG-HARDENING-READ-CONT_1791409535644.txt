PHASE OBJECTIVE

Harden and formalize the existing Service Catalog READ contract.

The goal is NOT to add a new healthcare domain.

The goal is to make Service listing and retrieval production-grade before any future module starts depending on the Service catalog.

This phase must establish:

1. deterministic tenant-scoped service listing
2. safe filtering
3. stable pagination
4. explicit ordering
5. consistent response contract
6. lifecycle-aware read behavior
7. cross-tenant isolation
8. regression coverage

Do not introduce service relationships to other healthcare entities.

==================================================
2. SERVICE LIST READ CONTRACT
==================================================

Harden:

GET
/api/v1/tenants/:tenantId/services

The endpoint must remain:

- authenticated
- tenant-scoped
- permission protected
- fail-closed

Required permission:

tenant.services.read

The tenant scope must always come from TrustedTenantContext.

The client must NOT be able to override tenant scope through:

- body
- query parameter
- header
- cookie
- arbitrary tenantId values

The route tenantId may be used only as the route scope input that is validated against TrustedTenantContext according to the existing architecture.

==================================================
3. PAGINATION
==================================================

Implement the project's established pagination style.

If no established pagination abstraction exists, use a simple page-based contract:

Query parameters:

page
pageSize

Defaults:

page = 1
pageSize = 20

Maximum:

pageSize = 100

Rules:

- page must be a positive integer
- pageSize must be a positive integer
- reject invalid values
- reject zero
- reject negative values
- reject non-numeric values
- reject unreasonable values above the maximum

Do not silently convert invalid values into valid values.

The response should expose enough metadata for a client to paginate safely, following existing API response conventions.

At minimum the contract must make it possible to determine:

- current page
- page size
- total matching records
- whether another page exists

Do not expose database implementation details.

==================================================
4. DETERMINISTIC ORDERING
==================================================

Service listing must have deterministic ordering.

Do NOT rely on database default ordering.

Use an explicit stable ordering.

Preferred:

createdAt ASC/DESC plus id as a deterministic tie-breaker

Choose the direction according to existing catalog conventions.

The important requirement is:

Two identical requests against unchanged data must return records in the same deterministic order.

If createdAt values are equal, id must provide deterministic ordering.

Document the ordering contract.

==================================================
5. FILTERING
==================================================

Add only filtering that is justified for the Service catalog.

At minimum support lifecycle/status filtering:

status

Example:

GET /api/v1/tenants/:tenantId/services?status=ACTIVE

Rules:

- validate status against the existing Service lifecycle enum
- invalid status must be rejected
- no arbitrary Prisma filter object
- no raw database expressions
- no client-controlled SQL/Prisma operators

Do NOT add:
- doctor filters
- department filters
- specialty filters
- branch filters
- facility filters
- patient filters

- appointment filters

Those relationships do not exist in this phase.

==================================================
