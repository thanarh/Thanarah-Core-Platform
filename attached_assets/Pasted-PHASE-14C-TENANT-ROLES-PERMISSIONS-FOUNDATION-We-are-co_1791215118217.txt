==================================================
1. PLATFORM VS TENANT AUTHORIZATION
==================================================

This distinction is mandatory.

Platform authorization:

PlatformUser
→ PlatformRole
→ PlatformPermission

Tenant authorization:

PlatformUser
→ TenantMembership
→ TenantRole
→ TenantPermission

These are different permission namespaces.

Never use a platform role as a tenant role.

Never use a tenant role as a platform role.

Never allow tenant permissions to grant platform permissions.

Never allow platform permissions to silently grant tenant permissions.

A platform administrator managing a tenant is still acting through platform authorization.

A tenant member operating inside a tenant is authorized through tenant membership + tenant roles/permissions.

==================================================
2. TENANT PERMISSION MODEL
==================================================

Create a central Prisma model for tenant-scoped permissions.

Use the existing naming, identifier, timestamp, and Prisma conventions.

A permission should have a stable machine-readable key.

Use a namespace that clearly separates tenant permissions from platform permissions.

Examples of future-style permissions may include:

tenant.members.read
tenant.members.manage

However, do NOT create a large healthcare permission catalog now.

Create only the minimum permission definitions required by this phase.

Permission identity must be unique.

Do not allow arbitrary client-created permission keys through public APIs.

==================================================
3. TENANT ROLE MODEL
==================================================

Create a central Prisma model for TenantRole.

A TenantRole belongs to a specific Tenant.

A tenant role must never be global across all tenants.

At minimum consider:

- id
- tenantId
- name
- stable key/code
- description where justified
- status if needed
- createdAt
- updatedAt

Use explicit constraints and normalization.

The same role key may exist in different tenants if that is architecturally appropriate.

A role in Tenant A must never authorize a user in Tenant B.

==================================================
4. ROLE / PERMISSION RELATIONSHIP
==================================================

Create an explicit many-to-many relationship:

TenantRole
    ↓
TenantRolePermission
    ↓
TenantPermission

Do not store permission arrays as uncontrolled JSON if the existing architecture favors relational authorization.

Permission assignment must be server-controlled.

Do not accept arbitrary permission IDs from an untrusted client and automatically trust them.

==================================================
5. MEMBERSHIP / ROLE ASSIGNMENT
==================================================

Connect TenantMembership to TenantRole through an explicit assignment model or equivalent.

The effective relationship must be:

TenantMembership
    ↓
TenantRole assignment
    ↓
TenantPermission

Role assignment must be tenant-scoped.

A membership from Tenant A must never receive a role belonging to Tenant B.

A role belonging to Tenant A must never be assigned to a membership belonging to Tenant B.

Enforce this at the service/repository/database level where practical.

Do not allow a request to assign a role by ID without validating tenant ownership.

==================================================
6. DEFAULT ROLES
==================================================

Do NOT blindly create a huge role catalog.

Define only the minimum default tenant roles required for the current SaaS foundation.

A reasonable foundation may include:

- OWNER
- ADMIN
- MEMBER

But inspect the existing architecture and Phase 14A/14B implementation first.

If default roles are created automatically, ensure:

- they belong to the correct Tenant
- their permission assignments are explicit
- they cannot accidentally become platform roles
- cross-tenant role reuse is impossible

Do not create healthcare-specific roles such as doctor, nurse, receptionist, accountant yet.

Those belong to later domain phases.

==================================================
7. OWNER PROTECTION
==================================================

Tenant OWNER is a privileged tenant role.

Define safe rules for OWNER management.

At minimum:

- a tenant must have a valid ownership path
- arbitrary users cannot assign themselves OWNER
- an ordinary tenant member cannot escalate themselves to OWNER
- role assignment must be authorized
- cross-tenant OWNER assignment must be impossible

Do not copy the platform OWNER rules blindly.

Tenant OWNER and Platform OWNER are different concepts.

Document the distinction.

If the architecture requires protection against removing the final OWNER, implement the minimum safe invariant:

A tenant must not accidentally become ownerless through an ordinary role-management operation.

Do not implement complex ownership transfer workflows yet unless necessary.

==================================================
8. TENANT AUTHORIZATION SERVICE
==================================================

Create a dedicated TenantAuthorizationService or equivalent policy service.

It must resolve permissions using trusted server-side context:

Authenticated Platform User
+
Trusted Tenant Context
+
Tenant Membership
+
Tenant Role(s)
+
Tenant Permission(s)

It must NOT trust:

- request body roles
- query permissions
- headers
- cookies
- client-provided role IDs
- client-provided permission IDs
- JWT tenant permissions supplied by the client
- tenant IDs alone

Authorization must fail closed.

==================================================
9. TENANT AUTHORIZATION GUARD
==================================================

Create a tenant-specific authorization mechanism without replacing PlatformAuthorizationGuard.

Keep these separate:

PlatformAuthGuard
PlatformAuthorizationGuard

Tenant authorization must be its own layer.

The conceptual order for future tenant routes is:

PlatformAuthGuard
→ TrustedTenantContext
→ TenantAuthorizationGuard

Do not make tenant authorization global.

Do not force tenant context onto health/readiness/docs.

Do not break existing public auth routes.

==================================================
10. REQUIRED PERMISSION DECORATOR
==================================================

If the existing architecture supports @RequirePermissions for platform authorization, do not silently reuse it for tenant permissions if doing so would make the permission namespace ambiguous.

Create a clearly separated tenant permission requirement mechanism if needed.

The distinction must be obvious in code.

For example, conceptually:

@RequirePlatformPermissions(...)
@RequireTenantPermissions(...)

Do not necessarily use these exact names if the existing project has a better convention.

The important requirement is:

Platform permission requirements and tenant permission requirements must never be confused.

==================================================

Use the TrustedTenantContext contract created in Correction 6.

Do not recreate a second tenant-context abstraction.

Tenant authorization must require trusted tenant context.

Do not resolve tenant identity directly from an arbitrary request parameter and treat it as trusted.

The membership and role must be validated against the trusted tenant.
