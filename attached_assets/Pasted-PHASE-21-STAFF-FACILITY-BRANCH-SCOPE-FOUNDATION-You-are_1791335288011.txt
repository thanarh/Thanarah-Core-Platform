==================================================
8. BRANCH / FACILITY SEMANTICS
==================================================

A Branch belongs to exactly one Facility.

A Facility belongs to exactly one Tenant.

A Staff member belongs to exactly one Tenant.

Therefore:

Staff may be assigned to:
- multiple facilities
- multiple branches

but ONLY within the same tenant.

A branch assignment automatically implies that the staff operates within that branch's facility.

Do NOT automatically create a separate StaffFacilityAssignment merely because a branch was assigned.

This would create redundant state.

However, if the existing architecture requires explicit facility assignment before branch assignment, document and enforce that rule instead.

Choose the simpler model that avoids contradictory scope records.

Facility/Branch assignment describes organizational scope.

It does NOT automatically create permissions.

Do NOT implement:

"assigned to branch → can read everything in branch"

Do NOT implement clinical access.

Do NOT implement patient access.

Do NOT implement appointment access.

Do NOT modify TenantPermission semantics.

The current model remains:

→ Tenant Membership

Phase 21 only creates the scope foundation.

10. STAFF STATUS
==================================================

Existing Staff statuses:

SUSPENDED
DEACTIVATED

Preserve current lifecycle.

Assignment behavior:

- ACTIVE staff may receive assignments.
- SUSPENDED staff must not gain effective operational scope.
- DEACTIVATED staff must not gain effective operational scope.

Do NOT delete assignments automatically when staff is suspended.

Preserve organizational configuration.

Do NOT automatically delete assignments when staff is deactivated.

Historical/configuration integrity should remain intact.

Whether assignments can be added to a suspended/deactivated staff must follow the simplest safe rule consistent with Phase 19.

Do not invent contradictory behavior.

==================================================
11. FACILITY / BRANCH STATUS
==================================================

Existing lifecycle:

Facility:
ACTIVE
SUSPENDED
DEACTIVATED

Branch:
ACTIVE
SUSPENDED
DEACTIVATED

Do not assign a staff member to an inactive/deactivated organizational unit unless there is a clear existing lifecycle rule that requires it.

Preferred behavior:

- ACTIVE facility → assignable
- SUSPENDED facility → reject new assignment
- DEACTIVATED facility → reject new assignment

For branches:

- ACTIVE branch → assignable
- SUSPENDED branch → reject new assignment
- DEACTIVATED branch → reject new assignment

Existing assignments should not be silently deleted when a Facility/Branch is suspended or deactivated.

Effective scope must be inactive when its parent organizational unit is inactive.

Do not create a second status engine.

==================================================
14. FACILITY ASSIGNMENT
==================================================

When assigning a facility:

Verify:

1. authenticated actor
2. TrustedTenantContext
3. staff exists
4. staff belongs to current tenant
5. facility exists
6. facility belongs to current tenant
7. facility is ACTIVE
8. staff is eligible
9. assignment does not already exist

Then create assignment.

Do not modify Staff itself.

Do not modify Facility itself.

Do not modify roles or permissions.

==================================================
15. BRANCH ASSIGNMENT
==================================================

When assigning a branch:

Verify:

1. authenticated actor
2. TrustedTenantContext
3. staff exists
4. staff belongs to current tenant
5. branch exists
6. branch belongs to current tenant
7. branch's facility belongs to current tenant
8. branch is ACTIVE
9. parent facility is ACTIVE
10. staff is eligible
11. assignment does not already exist

Then create assignment.

Do not create a facility assignment automatically unless the architecture explicitly requires it.
