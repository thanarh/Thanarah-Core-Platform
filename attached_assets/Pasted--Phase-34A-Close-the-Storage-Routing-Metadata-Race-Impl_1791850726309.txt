# Phase 34A — Close the Storage Routing Metadata Race

Implement a focused correction to the current TenantStorageActivationService. First inspect the actual working tree and current implementation because the previous review reported a clean Git status.

## Primary issue

Index readiness is checked against a tenant storage target before the registry transaction. The target is fetched again inside the transaction, but `databaseName` and `connectionReference` are not compared with the values that were verified.

Ensure the target activated by the transaction is exactly the target whose indexes were checked.

## Required changes

1. Inspect all code paths that can update tenant storage routing metadata, including `databaseName`, `connectionReference`, provider, target identity, status, and primary designation.
2. Establish an explicit invariant for routing metadata during activation.
3. Use the narrowest safe approach consistent with the existing architecture:
   - Either make routing metadata immutable after registration through all supported application paths, or
   - Add a version/compare-and-verify mechanism that detects changes between index preflight and registry activation.
4. Ensure activation aborts without registry mutation when the verified routing identity no longer matches the target inside the transaction.
5. Ensure the same invariant applies to primary-target switches.
6. Do not trust client-provided physical database names, connection strings, or cluster identifiers.
7. Do not claim MongoDB index DDL and the central Prisma transaction are atomic.
8. Do not add cluster rotation, automatic provisioning, migration, archive routing, or sharding.

## Tests

Add focused tests that prove:
- A changed `databaseName` between index verification and activation is rejected.
- A changed `connectionReference` between verification and activation is rejected.
- A failed primary switch leaves the previous primary unchanged.
- Failure after the first attempted registry mutation does not leave a partial primary switch.
- Existing activation conflict, readiness failure, and concurrent service-call behavior remain correct.

Keep unit tests deterministic. Do not pretend mocked locks prove real MySQL/MariaDB locking behavior.

Do not run container-backed Phase 30 integration tests or migrations without separate approval.

## Restrictions

- No production connections.
- No secret inspection or output.
- No patient-data changes.
- No staging or commits.
- Do not use `--no-verify`.

## Validation

Run the focused activation, registry, Mongo storage, and client-manager unit tests, plus available build, type-check, lint, formatting, and `git diff --check` commands.

Report exact files changed, test results, remaining concurrency limitations, and final Git status. Stop after reporting.
